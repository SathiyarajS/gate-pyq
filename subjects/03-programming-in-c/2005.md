**Type / marks:** MCQ, 1 mark(s).

**Independently derived answer:** C

**Paraphrased problem context:** Interpret C declaration int (*f)(int *). A function taking int* and returning int; B function taking int and returning int*; C pointer to function taking int* and returning int; D function taking int* and returning a function pointer.

## Solution

In int (*f)(int *), the parentheses make f a pointer. Its target is a function taking one int-pointer argument and returning int. Thus C; it is not a function returning a pointer.

Teaching detail:
Read outward from f. The parentheses bind *f before the following parameter list, so f is a pointer. Its pointed-to object is a function whose parameter is int* and whose return type, written at the left, is int. Without parentheses, int *f(int*) would instead declare a function returning int*. That binding distinction gives C.

# GATE 2005: Q31 (printed CS Q31)

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203225/GATE2005.pdf#page=4), physical page 4. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** MCQ, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** D

**Paraphrased problem context:** void foo(int n, int sum){int k=0, j=0;if(n==0)return;k=n%10;j=n/10;sum=sum+k;foo(j, sum);printf("%d,", k);} main sets a=2048, sum=0; calls foo(a, sum); prints sum with newline. Output? A8, 4, 0, 2, 14; B8, 4, 0, 2, 0; C2, 0, 4, 8, 14; D2, 0, 4, 8, 0.

## Solution

Calls peel off digits 8, 4, 0, 2, but each prints only after its recursive child returns. Thus the visible digits are 2, 0, 4, 8. The sum parameter is passed by value, so main’s sum stays 0. Assuming the usual stdio declaration, the output is 2, 0, 4, 8, 0 followed by a newline, option D; the commas come from the inner printf format.

Teaching detail:
Each call stores its own last digit k before recursively processing the remaining prefix. Because printing occurs after the child returns, digits appear from most significant to least:2, 0, 4, 8. The sum variable is a by-value local parameter, so changes do not propagate back into main’s sum. Main consequently appends 0, giving D. This question combines recursive output order with parameter passing, not a digit-sum algorithm that returns its result.

# GATE 2005: Q32 (printed CS Q32)

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203225/GATE2005.pdf#page=4), physical page 4. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** MCQ, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** D in ordinary C compilation

**Paraphrased problem context:** Program declares double foo(double) before main. main declares double da, db, obtains da through omitted input code, and assigns db=foo(da). Later definition double foo(double a){return a;}. If the initial declaration is removed, choose A no diagnostic; B harmless warnings; C type-mismatch warnings with unintended results; D compile errors. Distinguish standard-required diagnostic from implementation severity.

## Solution

Without the declaration, foo is called before its type is known. Modern C requires a declaration; historical implicit-int rules would assume an int-returning function, which conflicts with the later double-returning definition. A diagnostic is therefore required, and conventional compilers reject the conflicting types, D. C specifies required diagnostics rather than an absolute distinction between a warning and a fatal error, so exact compiler behavior depends on mode/extensions. The commented input of da is understood as omitted input code, as the prompt intends.

Teaching detail:
The early declaration tells the compiler that the call returns double. Removing it means a modern C compiler encounters an undeclared function call; older implicit-int conventions instead assume int, which conflicts with the later double definition. A diagnostic is required, and ordinary compiler modes reject the conflicting types, making D the conventional choice. The standard does not mandate the user-interface label warning versus error, so that distinction remains qualified.

# GATE 2005: Q61 (printed CS Q61)

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203225/GATE2005.pdf#page=7), physical page 7. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** MCQ, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** A under C90; modern C needs a diagnostic

**Paraphrased problem context:** Line 3 of historical C code is fro(I=0, I<N, I++); inside int main(){int I, N; ...}. During object-module creation is the response A no compilation error; B lexical error only; C syntactic error only; D both? Preserve the printed identifier fro and comma-separated expressions, not a repaired for loop.

## Solution

The printed line is fro(I=0, I<N, I++); with commas, not semicolons. Lexically fro is a valid identifier, and syntactically this is a function call with three arguments, not a for statement. Under the historical C90 implicit-function-declaration rule, an object module can be produced, so A is the intended compilation-stage answer; a missing definition may fail at link time. In C99 and later the undeclared function requires a diagnostic, but this is not a lexical or grammar error of the kind offered. The argument side effects also give undefined runtime behavior under C90 because I is modified more than once without an intervening sequence point; no runtime result is asserted. Both reproductions preserve fro and commas.

Teaching detail:
The lexer accepts fro as an ordinary identifier. The grammar accepts the following parentheses as a function call whose three arguments are I=0, I<N, I++. Thus misspelling for does not by itself create a lexical or grammar error. Older C allowed an implicit function declaration; an undefined fro may be discovered later by the linker. Modern C requires a diagnostic for the undeclared function, and runtime side effects are separately problematic. The intended old compilation-stage answer must not be presented as portable modern C.
