

# GATE 1999: Q68 (printed B Q11(b))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203805/GATE1999.pdf#page=7), physical page 7. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Copy p’s old payload into a new successor, then store D at p; this inserts the value in sequence but changes node identity.

**Essential problem context (paraphrased):** Write a constant-time algorithm to insert data D just before a node whose address p is given in a singly linked list. State any limitation of the method.

## Solution

With only p and no predecessor, one cannot in general redirect the predecessor’s next pointer in constant time while preserving the identity and payload of the existing node p. The standard answer implements insertion in the logical sequence by moving p’s old payload one node forward:

insert_before_value(p, D):
    require p != NULL
    q := allocate_node()        // assumed O(1); handle allocation failure
    q.data := p.data
    q.next := p.next
    p.data := D
    p.next := q
    return p                  // address now containing the inserted value

Before: ... → p:[old] → successor
After:  ... → p:[D]   → q:[old] → successor

The prefix still points to p, so no predecessor lookup is needed. The old data and suffix order are preserved. The method also works when p is the head or the tail. If an external tail pointer is maintained and p was the tail, update tail:=q.

The number of pointer and fixed-size data operations is constant. This assumes payload copying and allocation are constant-time. It does not preserve the old element’s address: external references to p now observe D. If “before the node p” literally requires the same p to remain the old node, the requested operation is impossible from p alone in a general singly linked list; supply its predecessor, an incoming-link pointer, or search from the head in O(n).

# GATE 1999: Q69 (printed B Q12(a))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203805/GATE1999.pdf#page=7), physical page 7. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 3 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** For every nonempty binary tree, L=F+1, including trees with one-child nodes.

**Essential problem context (paraphrased):** In a nonempty binary tree, a full node has exactly two children. Prove by induction on height that the number of leaves equals the number of full nodes plus one.

## Solution

Use strong induction on the height h, taking a leaf to have height zero. Let L(T) and F(T) count leaves and full nodes in T.

Base h=0: T is a single leaf, so L=1 and F=0, giving L=F+1.

Induction hypothesis: the identity holds for every nonempty binary tree of height less than h. Consider a tree T of height h>0. Its root has one or two children.

If it has one child, the unique child subtree T₁ has smaller height. The root is neither full nor a leaf, so L(T)=L(T₁) and F(T)=F(T₁). By induction L(T)=F(T₁)+1=F(T)+1.

If it has two children with subtrees T₁,T₂, both have smaller height. Here L(T)=L(T₁)+L(T₂) and F(T)=1+F(T₁)+F(T₂), because the root itself is full. Substituting the two induction hypotheses gives L(T)=F(T₁)+1+F(T₂)+1=F(T)+1.

These cases exhaust all roots, proving the claim. The qualification “nonempty” matters: an empty tree has zero leaves and zero full nodes, so the formula would not hold there. It is unnecessary to assume every internal node is full.

# GATE 1999: Q70 (printed B Q12(b))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203805/GATE1999.pdf#page=7), physical page 7. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** GateForum: [1,4,2,7,5,6,3] → [2,4,3,7,5,6]. GFG: [1,4,2,7,5,6,3] → [2,4,3,7,5,6].

**Essential problem context (paraphrased):** Insert the specified sequence into an initially empty min-heap and draw the final heap and its state after deleting the root. Source discrepancy: GateForum p11 gives 7,6,5,4,3,2,1; GFG p7 visibly gives 7,6,5,4,2,3,1. Both are solved separately below; no official original is available to adjudicate.

## Solution

A binary min-heap has complete-tree shape and each parent no larger than either child. Store it in level order. On insertion append at the next free position and swap upward while smaller than its parent. Do not sort the whole array: a heap is only partially ordered.

GateForum sequence 7,6,5,4,3,2,1 gives these successive level-order arrays:
[7]
[6, 7]
[5, 7, 6]
[4, 5, 6, 7]
[3, 4, 6, 7, 5]
[2, 4, 3, 7, 5, 6]
[1, 4, 2, 7, 5, 6, 3]

The resulting tree is:
             1
          /     \
         4       2
        / \     / \
       7   5   6   3

Delete the root by moving the final element 3 into its position and removing that final slot. This gives [3,4,2,7,5,6]. Swap 3 with its smaller child 2, giving [2,4,3,7,5,6]. Now 3≤6, so downward repair stops. The final tree is:
             2
          /     \
         4       3
        / \     /
       7   5   6

GFG instead orders the last three insertions as 2,3,1. Its successive arrays are:
[7]
[6, 7]
[5, 7, 6]
[4, 5, 6, 7]
[2, 4, 6, 7, 5]
[2, 4, 3, 7, 5, 6]
[1, 4, 2, 7, 5, 6, 3]

Although the intermediate states differ, the final heap coincides with the GateForum heap in this particular case. Its root-deletion result therefore also coincides. Preserving both source sequences is still important: agreement of the final answer does not establish that the printed questions were identical.

# GATE 1999: Q86 (printed B Q21)

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203805/GATE1999.pdf#page=9), physical page 9. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Under standard B-tree key occupancy: minimum 2m^(h−1)(m−1); maximum (2m−1)^h(2m−2).

**Essential problem context (paraphrased):** In a B-tree, every non-root internal node has between m and 2m−1 children inclusive. The root is at level 0; all leaves are at level h≥1. Derive minimum and maximum numbers of records in the leaf nodes.

## Solution

State the usual B-tree assumptions explicitly: m≥2, an internal node with c children has c−1 records, the non-leaf root has 2 through 2m−1 children, and non-root leaves carry between m−1 and 2m−2 records. The printed child bound alone does not independently specify leaf capacity; these are the conventional B-tree occupancy rules, not B+ tree rules or the alternative maximum-2m convention.
For the minimum, choose two root children and m children at every internal level below the root. The number of leaves is then Lmin=2m^(h−1): for h=1 there are two leaves; each further level multiplies their count by m. Filling each leaf with m−1 records gives Rmin=2m^(h−1)(m−1).
For the maximum, root and all other internal nodes have 2m−1 children, so Lmax=(2m−1)^h. Filling every leaf with 2m−2 records gives Rmax=(2m−1)^h(2m−2). Both bounds are attained by uniformly minimally or maximally occupied levels.
These counts exclude records in internal nodes. For example m=2,h=1 gives 2 to 6 leaf records (2 leaves×1 up to 3 leaves×2), not the 3 to 8 total records including the root. If only the literal internal-child bound is permitted without standard leaf-occupancy rules, leaf record counts are underdetermined; only the leaf-node bounds follow with the usual root rule.
