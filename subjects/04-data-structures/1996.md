**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203937/GATE1996.pdf#page=2), physical page 2. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** MCQ, 1 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** A under the intended linked-list operation model: statements ii and iii

**Essential problem context (paraphrased):** Assess FIFO for stacks, broad linked-list efficiency, circular queues reusing array slots, and LIFO for queues.

## Solution

A stack is LIFO, not FIFO; a queue is FIFO, not LIFO. In a circular array queue, the rear wraps around to locations freed by dequeues, so statement iii is correct. Linked lists permit constant-time insertion or deletion when the relevant node or predecessor is already known, avoiding array shifts; this motivates statement ii and the intended pair ii,iii. However, the assertion that linked lists are more efficient for almost all basic operations is not a mathematical universal: indexed access and cache-local traversal often favor arrays, and locating a node can require linear time. The operation and representation model must be specified.

# GATE 1996: Q13 (printed A Q1.13)

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203937/GATE1996.pdf#page=2), physical page 2. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** MCQ, 1 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** C

**Essential problem context (paraphrased):** Why can separate chaining be preferable to open addressing: better worst-case search, less storage, easier deletion, or another claim?

## Solution

In chaining, keys in a bucket form a separate collection. Once the key and necessary predecessor are found, deletion simply unlinks it without changing the search path for other keys. In open addressing, clearing a slot outright may incorrectly terminate a later probe, so deletion needs tombstones or careful reorganization. Both approaches can have linear worst-case search, and chaining normally incurs pointer or container overhead. The reliable advantage among these claims is therefore easier deletion, C, rather than a universal space or worst-case-time improvement.

**Official answer:** Not available; no official key located.

**Independently derived answer:** C: g,c,d,b,f,e,a

**Essential problem context (paraphrased):** For root a with left subtree b(c(g),d) and right subtree e(f), find the postorder traversal.

## Solution

Postorder visits the complete left subtree, then the complete right subtree, then the root. Within b, visit g before its parent c, then d, then b: g,c,d,b. Within e, visit f before e: f,e. Concatenate those two lists and finally append a, yielding g,c,d,b,f,e,a. The exact left-versus-right placement of a sole child does not affect postorder. Visiting a before its subtrees would be preorder, not the requested traversal.

## Solution

A search path obeys every ancestor constraint, not merely the immediately preceding comparison. Maintain an open interval of permissible keys, initially (−∞,+∞). When a probe is below 43, searching right raises the lower bound to that probe. When a probe is above 43, searching left lowers the upper bound.

After 61, every later probe must lie in (−∞,61).
After 52, every later probe must lie in (−∞,52).
After 14, every later probe must lie in (14,52).
After 17, every later probe must lie in (17,52).
After 40, every later probe must lie in (40,52).
The final probe is 43, so the search succeeds.

All probes meet the bounds. A witnessing BST can be built as a chain with these keys, taking the left or right child according to each comparison with 43. Thus the bound test proves existence, rather than just failing to find an error.

Source difference: GateForum prints 17 as the fourth probe; GFG prints 11. With 17 the sequence is valid. With 11 it is invalid, because after visiting 14 the search for 43 must stay in the right subtree of 14, whose keys exceed 14. The 11 variant therefore has the opposite answer.

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203937/GATE1996.pdf#page=8), physical page 8. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Official answer:** Not available; no official key located.

**Independently derived answer:** Under the intended full row/column order: i=j=1. Under the literal restricted quantifier: not guaranteed.

**Essential problem context (paraphrased):** An n×n integer array is intended to increase along every row and every column. Where is its minimum? The reproduction quantifies both inequalities only for i,j∈[1,n−1], which is narrower than full row/column sorting.

## Solution

Under the standard partially sorted matrix interpretation, A[1,1]≤A[i,j] for every cell: move downward from (1,1) to (i,1), then rightward to (i,j), using monotonicity at each step. With strict comparisons and n>1 this makes A[1,1] the unique minimum; the requested blanks are i=1 and j=1. For n=1 the only cell is trivially the minimum.

There is a literal specification issue. Both reproductions attach i,j∈[1,n−1] to both comparisons A[i,j]<A[i,j+1] and A[i,j]<A[i+1,j]. This does not constrain the last row horizontally or the last column vertically. In particular, A[n,n] appears in neither type of comparison. For n=2, the matrix [[1,2],[3,−100]] satisfies the printed comparisons 1<2 and 1<3, yet its minimum is at (2,2).

The usual intended definition instead quantifies horizontal comparisons for 1≤i≤n,1≤j<n, and vertical comparisons for 1≤i<n,1≤j≤n. The answer (1,1) follows from that corrected definition, not from the restricted literal one. This caveat also applies to the insertion procedure in the next subpart.

# GATE 1996: Q72 (printed B Q14(b))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203937/GATE1996.pdf#page=8), physical page 8. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, Unallocated leaf; group total 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Compare x to A[i+1,j],A[i,j+1]; choose their minimum; shift it up/left; advance i or j; finally write x.

**Essential problem context (paraphrased):** Delete the smallest element of an n×n row- and column-increasing array. Insert x, smaller than every item of the last row and last column, in O(n) time. Complete: i:=1;j:=1;A[i,j]:=x; while (x>blank or x>blank) do if A[i+1,j]<blank then begin A[i,j]:=A[i+1,j];i:=i+1 end else begin blank end; A[i,j]:=blank. Assume the intended full monotonicity and distinct inserted value.

## Solution

A complete hole-moving version is:
i:=1; j:=1; A[i,j]:=x;
while (x>A[i+1,j]) or (x>A[i,j+1]) do
begin
  if A[i+1,j]<A[i,j+1] then
  begin A[i,j]:=A[i+1,j]; i:=i+1 end
  else
  begin A[i,j]:=A[i,j+1]; j:=j+1 end
end;
A[i,j]:=x.

Treat the current cell as a hole until the final assignment. If both children are greater than x, x belongs there. Otherwise the smaller of the downward and rightward neighbors is the smallest candidate that can fill the hole without violating either row or column order. Move it into the hole, advance to its old position, and repeat. Along the moved path, predecessors remain smaller than the element shifted into place; untouched cells preserve their old comparisons. The terminal hole receives x.

Each iteration increases i+j by one, hence there are O(n) iterations and O(1) extra storage. The given strict upper bound on x prevents the hole from entering the last row or last column: a boundary neighbor is greater than x and cannot be the smaller neighbor selected while the loop is true. Thus the two neighbor accesses are safe for n≥2. Without that promise use explicit bounds or +∞ sentinels.

Distinct x is a sufficient extra condition for preserving strict order. Without it the guarantee can fail: consider [[0,10,40],[20,30,50],[60,70,80]] with x=10. Here x is below every last-row/column entry, yet the procedure stops with adjacent equal values in the first row. Equal entries can sometimes occupy incomparable cells, but strict preservation is not guaranteed by the printed promise. If duplicates are allowed, interpret sorted as nondecreasing instead. Finally, the literal source quantifier omits boundary comparisons, so the algorithm relies on the intended full row/column definition discussed in part (a).

**Essential problem context (paraphrased):** Insert K,R,P,C,S,N,Y,T,J,M in that order into slots 0,…,9 using linear probing and h(x)=(ord(x)−ord('a')+1) mod10. The input is uppercase while the formula uses lowercase a; distinguish alphabet-position normalization from literal uppercase ASCII. Which insertions collide?

## Solution

With alphabet positions (equivalently lowercasing each character before applying the formula), the home slots are K1,R8,P6,C3,S9,N4,Y5,T0,J0,M3. The first eight insertions find empty slots. J collides at 0 with T and at 1 with K, then occupies 2. M collides at 3,4,5,6, occupied respectively by C,N,Y,P, then occupies 7. Thus J and M are exactly the insertions that encounter collisions.

The final normalized table is 0:T,1:K,2:J,3:C,4:N,5:Y,6:P,7:M,8:R,9:S. Every character appears once and all ten slots are filled.

For literal uppercase ASCII with the printed lowercase 'a', ord(uppercase)=ord(lowercase)−32. Therefore each home slot is shifted by −32≡−2 modulo10. Linear probing is circular and the whole table rotates by the same amount. Homes become 9,6,4,1,7,2,3,8,8,1, and the final table is 0:J,1:C,2:N,3:Y,4:P,5:M,6:R,7:S,8:T,9:K. J and M still collide.
