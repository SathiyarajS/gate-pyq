**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204113/GATE1994.pdf#page=1), physical page 1. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** MCQ, Unallocated leaf; group total None mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** A: static allocation in the historical implementation model

**Essential problem context (paraphrased):** Why did the historical FORTRAN implementations described not permit recursion: static allocation, dynamic allocation, absent hardware stacks, or impossibility on some machines?

## Solution

A single statically allocated location for each local variable provides only one activation’s storage. A recursive call would overwrite values still needed by its caller, so that implementation cannot support general recursion without changing its storage scheme. A stack of activation records is the usual solution; a hardware stack is not essential because software can implement one. Thus A explains the historical restriction. It is not a claim about all modern Fortran: later standards and implementations support recursive procedures with appropriate activation storage.

**Official answer:** Not available; no official key located.

**Independently derived answer:** A

**Essential problem context (paraphrased):** Is unrestricted goto harmful because verification is harder, runtime rises, memory rises, or generated code is necessarily longer?

## Solution

Arbitrary jumps can create tangled control flow with many entry points and difficult-to-track invariants. This makes local reasoning about a block’s preconditions and postconditions harder, so program verification and maintenance suffer. A jump itself need not increase runtime, data storage or machine-code length; those effects depend on the program and compiler. The objection is therefore structural reasoning, not a universal performance penalty. Structured conditionals and loops make control-flow boundaries more explicit.

**Essential problem context (paraphrased):** Why generate intermediate code for an abstract machine: easier lexing, availability of syntax-directed rules, frontend portability, or inability to generate real machine code directly?

## Solution

An intermediate representation separates language analysis from target-machine details. The same frontend can translate a source language into that representation, while different backends generate code for different processors. This improves portability and reuse. Direct generation of machine code is possible, so D is false. Syntax-directed translation can generate an IR, but its existence is not the main abstract-machine benefit, and lexical analysis does not become fundamentally easier merely because an IR is chosen.

## Solution

A CFG can describe nested statements, recursive syntactic structures and identifier shapes of unbounded length. Checking that a particular identifier was previously declared requires matching that name against the declarations valid in its scope, not merely recognizing a syntactic category. Compilers therefore use symbol tables and semantic analysis for this context-sensitive condition. The claim concerns unrestricted identifiers and general programs; a finite fixed universe could be encoded into a much larger grammar, but that is not the usual language model.

**Essential problem context (paraphrased):** Which argument can expose different results between call-by-name and call-by-reference: constant, array address, whole array, or an array element?

## Solution

For an actual argument a[i], call-by-reference fixes the target location at call time. Call-by-name reevaluates the argument expression each time the formal is used. Thus an array element whose index can change demonstrates the difference. **Essential problem context (paraphrased):** Match BNF, lexical analysis, YACC and recursive-descent parsing with general CFGs, regular expressions, LALR(1), LL(1).

## Solution

Backus–Naur form is a notation for context-free grammar productions. Lexical token patterns are commonly specified by regular expressions and recognized by finite automata. Traditional YACC constructs an LALR(1) parser. A predictive recursive-descent parser uses LL(1) choices, with one-token lookahead selecting a production. Thus the requested mapping is d,a,b,c. General recursive descent can also use backtracking or more lookahead, so the LL(1) match refers to its standard nonbacktracking predictive form.

# GATE 1994: Q75 (printed B Q22(i))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204113/GATE1994.pdf#page=6), physical page 6. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, Unallocated leaf; group total 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** 2, 2, 2 (without separators, 222).

**Essential problem context (paraphrased):** main declares global integer r. Procedure two, declared directly inside main, executes write(r). Sibling procedure one declares its own local r, assigns it 5, then calls two. main assigns its r=2 and executes two; one; two. What values are printed under static scoping?

## Solution

Static, or lexical, scoping resolves a name by the nesting of declarations in the program text, not by whichever procedure happened to call the current procedure. Procedure two has no local declaration of r. Its immediately enclosing lexical scope is main, so every reference to r in two denotes main's r. Procedure one's local r is in a sibling procedure's scope and is not visible inside two.

After main assigns r=2, its first call to two prints 2. Next main calls one, which creates a separate local r and sets that local variable to 5. The call from one to two still resolves two's r to main's unchanged variable and therefore prints 2. Returning from one removes its local activation without changing main's r. The final direct call to two again prints 2.

Thus the sequence of values is 2,2,2. The pseudocode uses write rather than writeln and requests no separators, so a literal output stream would commonly appear as 222. Formatting conventions do not change the three values. Missing statement punctuation in the GateForum reproduction is treated as a typesetting defect; the sequence of actions is explicit and the GFG reproduction corroborates it.

# GATE 1994: Q76 (printed B Q22(ii))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204113/GATE1994.pdf#page=6), physical page 6. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, Unallocated leaf; group total 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** 2, 5, 2 (without separators, 252).

**Essential problem context (paraphrased):** main declares global integer r. Procedure two, declared directly inside main, executes write(r). Sibling procedure one declares its own local r, assigns it 5, then calls two. main assigns its r=2 and executes two; one; two. What values are printed under dynamic scoping?

## Solution

Under dynamic scoping, resolve an unbound local name by searching active callers, nearest first. Procedure two itself has no r. In the first call main→two, the closest active declaration is main's r, already set to 2, so two prints 2.

The second relevant call chain is main→one→two. Procedure one has an active local r initialized to 5. The search from two finds that declaration before reaching main, so this invocation prints 5. Procedure two merely reads the variable; it does not copy the value into main's r or assign to either declaration.

After one returns, its local r is no longer in the active call chain. The last main→two call therefore finds main's original r=2 and prints 2. The resulting sequence is 2,5,2, or 252 if ordinary write operations introduce no spaces. The key distinction is lifetime plus dynamic caller order: the same body of two can access different storage on different calls under dynamic scoping, whereas static scoping would always bind its r to main's lexical declaration. This result concerns the hypothetical dynamic-scoping interpretation requested, not the default rules of Pascal.

# GATE 1994: Q77 (printed B Q23)

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204113/GATE1994.pdf#page=7), physical page 7. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Use synthesized code/place attributes and a fresh memory temporary for each addition; assign by LOAD expression.place; STORE target.

**Essential problem context (paraphrased):** Generate code for A→id:=E; E→E+T | T; T→(E) | id. The target has one accumulator R and only LOAD x (R:=mem[x]), STORE x (mem[x]:=R), ADD x (R:=R+mem[x]). Provide a syntax-directed translation.

## Solution

Give every E and T synthesized attributes code (an instruction list) and place (a memory address containing its value). An identifier token has its declared address id.addr. Let newtemp() allocate a fresh, non-aliasing memory cell and || concatenate instruction lists. The following bottom-up semantic rules form a complete syntax-directed definition.

T→id: T.code=[]; T.place=id.addr.
T→(E): T.code=E.code; T.place=E.place.
E→T: E.code=T.code; E.place=T.place.
E→E1+T: choose t=newtemp(); E.code=E1.code || T.code || [LOAD E1.place, ADD T.place, STORE t]; E.place=t.
A→id:=E: A.code=E.code || [LOAD E.place, STORE id.addr].

The invariant is that executing a subtree's code leaves its value in its designated memory cell. Identifier leaves already satisfy this. Parentheses and E→T preserve it. In an addition, both operands are available in memory after their code has run; LOAD fetches the left one and ADD combines the right one without needing a second register. STORE preserves the result for enclosing expressions. Fresh temporaries prevent a right subtree from overwriting the saved left value. The final assignment changes the target only after the whole expression has been evaluated, so x:=x+y also works.

For x:=a+(b+c), first emit LOAD b; ADD c; STORE t1. Then LOAD a; ADD t1; STORE t2. Finally LOAD t2; STORE x. This deliberately simple scheme may contain redundant loads/stores, but optimization is not required. It uses exactly the three allowed instruction types and handles arbitrary nesting, unlike a scheme that leaves an unprotected partial result only in R.
