**Official answer:** Not available; no official key located.

**Independently derived answer:** Expansion changes code size and the addresses needed for the symbol table

**Essential problem context (paraphrased):** Why expand macros in pass one rather than pass two?

## Solution

A macro invocation can expand into several instructions, data definitions and labels. Pass one must account for their sizes to advance the location counter correctly and assign addresses to all later symbols. Deferring expansion until after that layout would invalidate those addresses or require another layout pass. Thus the standard macro assembler expands before or during its first layout pass. A separately implemented macro preprocessor can perform the same work before the nominal assembler passes; the essential requirement is expansion before final address assignment.

**Independently derived answer:** Track the address assigned to the next instruction or data item

**Essential problem context (paraphrased):** What is the purpose of an assembler’s instruction location counter?

## Solution

The location counter starts from the selected origin and advances by each assembled instruction or reserved data size. A label encountered at a statement is assigned the current location, enabling the symbol table to record its address. Directives such as ORG can change the counter explicitly. This is a compile/assembly-time layout variable, not the processor’s runtime program counter. Its final difference from the origin can also help determine section length, subject to separate sections and origin changes.

**Official answer:** Not available; no official key located.

**Independently derived answer:** Option letters unresolved; LFOLLOW may differ, and RFOLLOW=FOLLOW under a productive-grammar convention

**Essential problem context (paraphrased):** FOLLOW(A) uses arbitrary sentential forms; LFOLLOW/RFOLLOW restrict to leftmost/rightmost forms. Both sources lose the L/R prefixes in choices A/B. Determine valid semantic relationships.

## Solution

Restricted derivations yield subsets of the ordinary FOLLOW set. For S→AB, A→a, B→b, ordinary and rightmost derivations expose Ab, so b belongs to FOLLOW(A) and RFOLLOW(A). Leftmost derivations must expand A before B, so LFOLLOW(A) is empty. This refutes the choices asserting all three always identical or all three always different. For productive grammars, rightmost derivations can realize the needed right context, giving RFOLLOW=FOLLOW. Without that convention, S→XB, X→Ab, B→B gives FOLLOW(A) containing b but no rightmost occurrence of A. Since A/B repeat the unqualified name FOLLOW in both copies, their intended exact comparisons and letters are not reconstructed silently.

**Official answer:** Not available; no official key located.

**Independently derived answer:** B, C, D under aligned LR(0)-core state numbering

**Essential problem context (paraphrased):** For one CFG, compare SLR(1) and LALR(1) tables: goto parts may differ; shifts identical; reductions may differ; errors may differ.

## Solution

Both constructions use the same LR(0) cores for transitions, so terminal shifts and nonterminal gotos coincide when corresponding states are identified. SLR places a completed A production on every token in FOLLOW(A). LALR instead uses the lookaheads propagated to that completed item, often a smaller set. Thus a cell that is a reduction or conflict in SLR may be an error or a different action set in LALR. Therefore shifts are identical but reduction/error entries may differ. Renaming state numbers does not count as a structural goto difference; conflict-resolution policies are separate from raw table construction.

**Official answer:** Not available; no official key located.

**Independently derived answer:** M2 0

**Essential problem context (paraphrased):** M1 calls M1(X+1) when X=0 and otherwise emits WORD X; M2 calls M2(X) when X=0 and otherwise emits WORD X+1. Which loops forever, and give a call.

## Solution

For M1 0, the recursive invocation receives 1. Its zero test fails, so it emits a word and stops; a nonzero initial argument likewise stops directly. In M2 0, the recursive call receives exactly 0 again, so every expansion repeats the same zero test and invocation with no progress. This causes unbounded expansion until a practical processor limit intervenes. The nonzero WORD branch cannot rescue that call because it is never reached. The analysis assumes expansion-time arithmetic and equality tests on X as intended.

## Solution

When pass1 encounters a literal operand, it records its value and storage needs in the literal table. Literal-pool directives or the end of a section determine placement, which must be included in layout before addresses are finalized. Thus entry into the table is a first-pass activity, distinct from outputting its bytes.

# GATE 1992: Q53 (printed B Q10(a))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204205/GATE1992.pdf#page=7), physical page 7. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, Unallocated leaf; group total None mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Call by value-result (copy-in/copy-out); capture the actual argument’s location at call time and copy back to that same location.

**Essential problem context (paraphrased):** For P(A[i]), where P has an integer formal parameter, a proposed implementation creates local z, sets z:=A[i], runs P’s body using z, then writes A[i]:=z. Identify the parameter-passing mechanism, judge correctness and give a small correction.

## Solution

The separate local variable receives the initial value and is copied back on return, so the intended mechanism is call by value-result, also called copy-in/copy-out. It is not call by reference, which uses the actual storage throughout execution, nor call by value, which never copies a final value back. Call by name re-evaluates an actual-argument expression in its caller environment on each use rather than using one private copied value.

The proposed copy-back re-evaluates A[i]. If the caller’s index changes during execution, it can select a different element from the one used at entry. For example initially i=2 and A[2]=10. Suppose the body changes the caller-visible index to 3 through a global reference and leaves the formal’s local value as 99. Re-evaluating A[i] on exit writes A[3]=99 instead of copying back into A[2]. An implementation must preserve the original actual location under the usual location-fixed value-result convention.

Small correction:
p:=address_of(A[i]);   {evaluate actual location in caller environment once}
z:=value_at(p);       {copy in}
execute P body with every occurrence of its formal bound to z;
value_at(p):=z;       {copy out to saved location}
If A is known not to change identity or base address, saving k:=i and using A[k] for both transfers is sufficient; saving the address is the general correction. Normal return is assumed, and with one parameter there is no multiple-copy-back ordering issue.

There is also a naming issue in the printed wording: P’s formal is named i, while the actual A[i] contains the caller’s i. They are different bindings. The body must substitute z for the formal, not literally search for the caller expression A[i] in the body. Merely assigning the formal does not itself change the caller’s separate index; the failure requires that the caller-visible index or array location can otherwise change. If that cannot happen, the original sequence happens to produce the right result.

program Test;
  procedure A;                 {outer A}

      y: A;
    end;

    B;
  end;

end.

## Solution

Assign lexical levels Test=0, A_outer=1, B=2 and A_inner=3. The declarations, not the dynamic call order, determine these levels. The call x:A in Test resolves to A_outer. The call y:A in B resolves to the nearest enclosing declaration of A, namely B’s own nested A_inner; it does not recursively invoke A_outer.

Immediately after x’s callee starts, before A_outer executes B, the stack and display are:
Stack bottom→top:
[Test frame: caller/runtime link]
[A_outer frame: dynamic link→Test; static link→Test;
 return continuation→after x:A; saved previous display[1]]
Display: D[0]→Test, D[1]→A_outer.
D[2] and D[3] have no active corresponding frames and are undefined/unused. Do not invent B or A_inner frames at this first instant.

A_outer then calls B, whose body calls A_inner at y. Immediately after y’s callee starts:
Stack bottom→top:
[Test]
[A_outer: DL→Test, SL→Test, return→after x:A, saved old D[1]]
[B: DL→A_outer, SL→A_outer, return→after B call, saved old D[2]]
[A_inner: DL→B, SL→B, return→after y:A, saved old D[3]]
Display diagram:
D[0] ──> Test
D[1] ──> A_outer
D[2] ──> B
D[3] ──> A_inner

The dynamic link names the calling activation, while the static link names the activation of the lexical parent. They happen to coincide throughout this simple nested call chain; their meanings remain different. A display-based implementation can replace static-chain access entirely, so the static links shown are explanatory rather than required additional storage. On entry at lexical level ℓ, save old D[ℓ] in the frame and set D[ℓ] to that frame; on return restore the saved value. Return addresses, saved registers and local-storage slots are conventional frame fields, but no particular byte sizes or actual locals are specified. The omitted body of A_inner has not yet executed at the requested second snapshot, so no additional calls or frames may be assumed.

# GATE 1992: Q55 (printed B Q11(a))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204205/GATE1992.pdf#page=8), physical page 8. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, Unallocated leaf; group total None mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Collect identifier-entry references in synthesized L.entries; assign T.type to them at D → T L ;.

**Essential problem context (paraphrased):** Add syntax-directed semantic rules to the ends of productions, without changing the grammar, so each identifier gets its declared type in the symbol table:
D → T L ;
T → int | real
L → L , id | id

## Solution

A synthesized list of symbol-table references solves the end-only restriction without needing to pass an inherited type into L before parsing it. Give T a synthesized attribute type and L a synthesized attribute entries. The lexical token id.entry is a reference to that identifier's symbol-table entry (or the declaration entry created for it in the current scope).

Attach precisely these actions at production ends:
D → T L ; { for each p in L.entries: p.type := T.type }
T → int { T.type := integer }
T → real { T.type := real }
L₀ → L₁ , id { L₀.entries := append(L₁.entries, id.entry) }
L → id { L.entries := [id.entry] }

The subscripts distinguish the two occurrences of L; they are attribute notation, not new grammar symbols. append constructs or extends a list of references, not copies of symbol-table records. On reduction of L → id, the one-element list is available. Each reduction of the recursive production adds one further identifier. By induction on the list length, the final L.entries contains exactly the identifiers in this declaration. At the D reduction both T.type and the complete list are available, so every listed entry receives the same type.

For real x,y,z;, T.type becomes real, the L lists successively become [x], [x,y], [x,y,z], and the final action assigns real to x, y, and z. All actions are at the right ends, and the original productions are untouched. Redeclaration detection and nested-scope lookup are separate symbol-table concerns. With a tail pointer or linked-list concatenation, building and processing a k-identifier list costs O(k) time and O(k) references.

# GATE 1992: Q56 (printed B Q11(b))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204205/GATE1992.pdf#page=8), physical page 8. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, Unallocated leaf; group total None mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Seven quadruples, ending in t7 = t3 or (t4 and t5); all operands are evaluated.

**Essential problem context (paraphrased):** Generate three-address quadruples in compiler generation order for (a+b) > (c+d) or a > c and b < d. Use usual precedence; partial/short-circuit evaluation is forbidden.

## Solution

The parse is ((a+b)>(c+d)) or ((a>c) and (b<d)), because arithmetic binds before comparison and and binds before or. Generate code in a left-to-right postorder traversal, storing each intermediate value in a fresh temporary. A quadruple is (operator, argument1, argument2, result):

1. (+, a, b, t1)
2. (+, c, d, t2)
3. (>, t1, t2, t3)
4. (>, a, c, t4)
5. (<, b, d, t5)
6. (and, t4, t5, t6)
7. (or, t3, t6, t7)

Thus t1=a+b, t2=c+d, and t3 is the first Boolean comparison. Independently t4 and t5 compute both comparisons in the second arm; t6 combines them, and t7 is the final Boolean value. All comparison and Boolean results are represented as Boolean values (or conventional 0/1 encodings), not jump destinations. Every operation executes even if t3 is already true or t4 is false. A jump-based short-circuit sequence would violate the explicit prohibition on partial evaluation.

There are seven internal nodes in the expression tree and one quadruple per node. Temporary names and the order of independent child computations can differ in valid implementations; this is one conventional compiler generation order, not a uniquely mandated register allocation.
