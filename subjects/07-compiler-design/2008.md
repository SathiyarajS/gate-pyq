

# GATE 2008: Q11 (printed CS Q11)

**Question:** [Official-source archive](https://drive.google.com/file/d/1popAHO-cX69oQEx_tD0wZXL1tTrBljeO/view), member CS/CS2008.pdf, physical page 3. Consult original wording and choices.

**Type / marks:** MCQ, 1 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** D

**Paraphrased problem context:** Which describes a handle in LR parsing?

(A) A position in a sentential form for the next shift or reduce operation
(B) A nonterminal whose production is used for the next reduction
(C) A production possibly used for a future reduction and the position of the next shift or reduce operation
(D) The production used in the next reduction and the position of its right-hand side in the sentential form

## Solution

1. Bottom-up LR parsing reverses a rightmost derivation: it replaces a production’s right-hand side by its left-hand-side nonterminal.
2. A handle must specify both which production to reduce and which occurrence of its right-hand side is the correct next one. Merely naming a position or a nonterminal is insufficient.
3. D gives exactly this production-and-position pair. A possible future reduction, as in C, is not necessarily the next handle.

**Official answer:** Not available; no official key located.

**Independently derived answer:** A

**Paraphrased problem context:** Why are some code optimizations performed on intermediate code?

(A) They enhance compiler portability to other target processors
(B) Program analysis is more accurate on intermediate code than machine code
(C) Dataflow-analysis information cannot otherwise be used for optimization
(D) Front-end information cannot otherwise be used for optimization

## Solution

1. Intermediate code abstracts away many machine-specific details, allowing one optimization pass to serve several target back ends.
2. This reuse makes it easier to retarget the compiler, which is the portability benefit in A.
3. B claims a universal analysis-accuracy advantage that does not follow. C and D incorrectly say dataflow/front-end information cannot otherwise be used; such information can also inform other compilation stages.

# GATE 2008: Q54 (printed CS Q54)

**Question:** [Official-source archive](https://drive.google.com/file/d/1popAHO-cX69oQEx_tD0wZXL1tTrBljeO/view), member CS/CS2008.pdf, physical page 11. Consult original wording and choices.

**Type / marks:** MCQ, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** A

**Paraphrased problem context:** Which are true? I: a language without globals or nested procedures, but with recursion, can use static storage allocation. II: multilevel access links/displays are needed only for languages with nested procedures. III: recursion cannot use dynamic storage allocation. IV: nesting and recursion require heap allocation and cannot use stack activation records. V: languages allowing a function to return a function cannot use only stack allocation for activation records.

(A) II and V only
(B) I,III,IV only
(C) I,II,V only
(D) II,III,V only

## Solution

1. Under the standard language-runtime assumptions, II and V are true, giving A. I is false: recursive calls can have arbitrarily many simultaneously live instances of local variables, so one statically allocated activation record per procedure is insufficient even without globals or nested procedures.
2. II is true: multilevel static access links/displays serve access to lexically enclosing procedures; without lexical nesting no multilevel environment chain is needed. III is false because dynamic stack allocation supports ordinary recursion.
3. IV is false because nested procedures and recursion alone can use stack activation records with static/dynamic links. V describes a returned nested function that can retain its defining environment after the creator returns: pure stack allocation cannot preserve that environment, so escaping environments need extended lifetime, normally heap allocation or copying.
4. The literal statement V is too broad without that escaping-closure assumption: a function may return a pointer to a global function, or a function with no captured environment, while ordinary activation records remain stack allocated. Thus A is the intended answer under the nested escaping-function interpretation, not a universal consequence of merely returning any function.

# GATE 2008: Q55 (printed CS Q55)

**Question:** [Official-source archive](https://drive.google.com/file/d/1popAHO-cX69oQEx_tD0wZXL1tTrBljeO/view), member CS/CS2008.pdf, physical page 11. Consult original wording and choices.

**Type / marks:** MCQ, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** B

**Paraphrased problem context:** An LALR(1) parser for G has shift-reduce conflicts if and only if:

(A) Its SLR(1) parser has shift-reduce conflicts
(B) Its LR(1) parser has shift-reduce conflicts
(C) Its LR(0) parser has shift-reduce conflicts
(D) Its LALR(1) parser has reduce-reduce conflicts

## Solution

1. The equivalence is with canonical LR(1), option B. An LALR state merges LR(1) states having the same LR(0) core and unions lookaheads. Suppose a merged state has a reduction A→α on lookahead a and a shift on a.
2. The reduction/lookahead pair came from some original LR(1) state. The shift item is in the shared LR(0) core, so it also occurred in that very original state. Thus the shift-reduce conflict already existed before merging.
3. Conversely a conflict in an original LR(1) state survives the merge. Merging can introduce reduce-reduce conflicts, but cannot create a new shift-reduce conflict. SLR/LR(0) may report conflicts avoided by finer LR(1) lookaheads.
