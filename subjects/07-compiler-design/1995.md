**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204046/GATE1995.pdf#page=1), physical page 1. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** MCQ, 1 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** C: −10

**Essential problem context (paraphrased):** Pascal executes X:=−10; Y:=20; if X>Y then if X<0 then X:=abs(X) else X:=2*X. What is X?

## Solution

The outer condition X>Y evaluates as −10>20, which is false. Its entire then statement, including the nested if and its else, is skipped. Therefore neither abs(X) nor doubling executes, and X stays −10. Pascal associates the else with the nearest unmatched if, namely the inner X<0 test. Treating that else as belonging to the outer test would incorrectly execute the doubling branch and obtain −20.

**Independently derived answer:** D: formal parameters

**Essential problem context (paraphrased):** In macro Add x,y with body Load y; Mul x; Store y, are x,y variables, identifiers, actual parameters or formal parameters?

## Solution

The names x and y appear in the macro definition and stand for values or text supplied by each invocation. They are therefore formal parameters. An invocation such as Add A,B supplies actual parameters A and B, which replace the corresponding formals during expansion. Although formal names are also identifiers in a broad lexical sense, “formal parameters” is the specific role asked here. They need not denote runtime storage variables of the expanded program.

**Independently derived answer:** C: III

**Essential problem context (paraphrased):** Which can definitely be recognized as a whole token without reading the next character: I begin, II program, III <>?

## Solution

The characters begin may be followed by another identifier character, producing an identifier such as beginning rather than the keyword begin. The same issue applies to program. The lexer therefore needs to determine the word boundary before deciding those tokens. Pascal’s <> is a complete relational operator with no longer operator having it as a prefix, so it can be recognized immediately after the second character. This is the longest-token principle, not a claim that keywords cannot ever be recognized.

**Essential problem context (paraphrased):** Grammar S→xxW {print1}, S→y {print2}, W→Sz {print3}. What is printed by a shift-reduce parse of xxxxyzz?

## Solution

The innermost y reduces to S first, printing 2. That S followed by z reduces to W, printing 3. The preceding xx and this W reduce to S, printing 1. **Official answer:** Not available; no official key located.

**Independently derived answer:** C: 2000 bytes without padding or a stored tag

**Essential problem context (paraphrased):** A record has one integer number and alternative fields (x,y:integer) or (p,q:real). With 4-byte integers and 8-byte reals, how much storage for 100 records?

## Solution

Alternative fields share the same region; the record does not store both variants simultaneously. The integer pair needs 8 bytes and the real pair 16, so the variant region must reserve their maximum, 16. Add the common integer field’s 4 bytes to get 20 per record, or 2000 for 100. This assumes the abstract packed/no-padding model and no separately stored discriminant, as the intended choices do. An implementation aligning 8-byte real fields might use 24 bytes per record instead; byte sizes alone do not determine actual ABI padding.

**Essential problem context (paraphrased):** Convert A+B*(C+D)/F+D*E to postfix using ordinary precedence and left associativity.

## Solution

First convert C+D to CD+, multiply by B to obtain BCD+*, and divide by F to obtain BCD+*F/. Ordinary left-associative addition then combines A with that term, before adding DE*, yielding ABCD+*F/+DE*+. Listed B is ABCD+*F/DE*++, which instead parses A+(B*(C+D)/F+D*E). These have the same value over exact arithmetic because addition is associative, explaining the intended B, but they are not identical parse-tree conversions and can differ with floating-point rounding. The distinction is retained rather than labeling the printed postfix exactly left associative.

# GATE 1995: Q60 (printed B Q9(a))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204046/GATE1995.pdf#page=6), physical page 6. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, Unallocated leaf; group total 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** mul(a, neg(add(b,c)))

**Essential problem context (paraphrased):** Translate a * −(b+c) into an abstract syntax tree.

## Solution

The parentheses force addition of b and c first. The minus sign immediately before the parentheses is unary negation, since it has only the parenthesized expression as operand. Multiplication then combines a with that negated result.

The tree is:
        *
       / \
      a  unary−
            |
            +
           / \
          b   c

Equivalently, its exact parenthesized representation is mul(a,neg(add(b,c))). Leaves are identifiers and internal nodes are operations. The abstract syntax tree need not contain separate parenthesis nodes because the tree structure already records grouping. It is important not to turn the unary minus into a binary subtraction with a missing left child. A code generator could evaluate add(b,c), negate its result, and finally multiply by a; the tree expresses that dependency regardless of the eventual instruction order.

# GATE 1995: Q62 (printed B Q10(a))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204046/GATE1995.pdf#page=6), physical page 6. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, Unallocated leaf; group total 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** First with assigns A.A=4 and A.B=V; second assigns B.A=X and B.B=Y.

**Essential problem context (paraphrased):** procedure T(U,V,X,Y:integer); var A:record A,B:integer end; B:record B,A:integer end; begin with A do begin A:=4; B:=V end; with B do begin A:=X; B:=Y end end. Identify the declarations bound to each A and B occurrence.

## Solution

There are six distinct declarations with these spellings: two outer record variables, outer A and outer B, and two integer fields inside each record. A field name belongs to its record’s field namespace; declaring field A does not replace the surrounding record variable A.

In “with A do”, the selector A is resolved before entering the with environment, so it denotes the outer record variable A. Within that body, unqualified field identifiers take precedence: the assignment A:=4 means outer-A.A:=4, while B:=V means outer-A.B:=V. V remains the procedure parameter.

That with scope ends at its end. Therefore the selector in the following “with B do” denotes the outer record B, not the field B from the preceding block. Within the second body, A:=X means outer-B.A:=X and B:=Y means outer-B.B:=Y. X and Y are parameters. The field declarations in the first record define A.A and A.B; those in the second define B.B and B.A. Parameter U is unused in the displayed reproduction. The literal 4 is preserved rather than silently replacing it with U.

# GATE 1995: Q63 (printed B Q10(b))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204046/GATE1995.pdf#page=6), physical page 6. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, Unallocated leaf; group total 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Remove the comma, use := for assignment, and replace the malformed/adjacent 2.5A with a valid expression such as 2.5*A if multiplication was intended.

**Essential problem context (paraphrased):** Identify errors in: if A > 1, then B = 2.5A else read(C);

## Solution

The comma after 1 is not allowed between an if condition and then. Delete it. The then branch needs a statement; B=... is a comparison expression, not Pascal assignment, so use B:=.... Neither comma nor = is an invalid token by itself: their placement/use is a syntactic error.

The character sequence 2.5A is not one valid Pascal numeric literal. A scanner may report an invalid numeric suffix, or tokenize it as the real literal 2.5 followed by identifier A, depending on its lexical rules. In the latter case the parser still rejects the adjacent operands because no operator connects them. Pascal has no implicit multiplication. If multiplication was intended, write 2.5*A; if the A was accidental, deleting it is a different possible repair.

Under the multiplication interpretation a corrected statement is “if A > 1 then B := 2.5*A else read(C);”. Whether assigning this real-valued expression to B is type-correct additionally depends on B’s declaration, which the question does not provide. Calling all three faults lexical is imprecise; the solution distinguishes token formation from grammar and typing.

**Discrepancy / qualification:** CS-1995-LEXICAL-TERMINOLOGY
