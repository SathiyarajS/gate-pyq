**Independently derived answer:** C

**Essential problem context (paraphrased):** What is the process of assigning actual load addresses and adjusting program address references: assembly, parsing, relocation, or symbol resolution?

## Solution

Step 1: Object code can contain address-dependent references expressed relative to an initially assumed location. Loading the program elsewhere requires assigning its actual locations.

Step 2: Address fields or relocation entries are adjusted to match those locations; this operation is relocation, C. Assembly translates symbolic instructions, parsing recognizes syntactic structure, and symbol resolution identifies which definition a name denotes. These can accompany linking/loading but are distinct tasks.

**Official answer:** Not available; no official key located.

**Independently derived answer:** A

**Essential problem context (paraphrased):** Which claim is false? An unambiguous grammar has identical leftmost and rightmost derivations; LL(1) parsing is top-down; LALR is more powerful than SLR; an ambiguous grammar cannot be LR(k) for any k.

## Solution

Step 1: Unambiguity means each generated string has one parse tree, hence one leftmost derivation and one rightmost derivation. It does not mean those two sequences of intermediate sentential forms are identical.

Step 2: For S→AB,A→a,B→b, the leftmost derivation is S⇒AB⇒aB⇒ab, while the rightmost one is S⇒AB⇒Ab⇒ab. The grammar is unambiguous, yet the derivations differ.

Thus A is false. LL(1) is top-down, LALR recognizes a strictly larger grammar class than SLR, and every LR(k) grammar is unambiguous.

**Essential problem context (paraphrased):** Caller variables begin x=10,y=3 and call func1(y,x,x) by reference, then print x,y. The callee’s formals are x,y,z and execute y=y+4; z=x+y+z. Choose 10,3; 31,3; 27,7; or none.

## Solution

Step 1: Rename the caller variables X=10,Y=3 to avoid confusing them with formal names. The call func1(Y,X,X) makes formal x alias Y, while both y and z alias the same caller variable X.

Step 2: y=y+4 changes X from 10 to 14. Then z=x+y+z reads 3+14+14=31 and stores 31 in X. Y is never assigned and remains 3.

The caller prints 31 and 3, B. Treating y and z as separate copies would miss the aliasing effect; this is reference-passing pseudocode, not ordinary C scalar call-by-value.

**Independently derived answer:** FIRST(E)={a,(}; FIRST(A)={+,*,ε}; FOLLOW(E)=FOLLOW(A)={),$}.

**Essential problem context (paraphrased):** Start symbol E; productions E→aA | (E), A→+E | *E | ε. Terminals a,(,),+,*. 

## Solution

E→aA begins with a; E→(E) begins with (, so FIRST(E)={a,(}. A’s alternatives begin with + and *, or are empty, giving FIRST(A)={+,*,ε}. Put end marker $ into FOLLOW(E) because E is the start symbol. E→(E) adds ) to FOLLOW(E). E→aA puts A at the end, so FOLLOW(E) is included in FOLLOW(A). A→+E and A→*E put E at the end, so FOLLOW(A) is included in FOLLOW(E). Iterating these inclusions reaches the fixed point FOLLOW(E)=FOLLOW(A)={),$}. Neither + nor * follows E in this grammar; those operators start A.

**Independently derived answer:** S.code = gen(L+":") || S1.code || E.code || gen("if "+E.varName+" == 0 goto "+L), where L=newlabel().

**Essential problem context (paraphrased):** S→repeat S1 until E. S1.code is body code; E.code computes a Boolean into E.varName (1=true,0=false). newlabel() returns a fresh label; gen(s) emits a code line.

## Solution

Associate the production with this semantic rule:

L = newlabel();
S.code = gen(L + ":")
         || S1.code
         || E.code
         || gen("if " + E.varName + " == 0 goto " + L);

Here || denotes concatenation of generated code strings, not Boolean OR. The resulting three-address layout is:
L:
    [body code]
    [compute E into t]
    if t == 0 goto L
    [next statement]

The body is before the condition so it runs at least once. A false result repeats; a true result falls through. E.code must be inside the loop because the condition is recomputed after every iteration. A fresh label for each production application avoids collisions when repeats are nested. No explicit exit label is necessary because the successful path falls through.

**Independently derived answer:** Exactly two parse trees; grammar is ambiguous.

**Essential problem context (paraphrased):** Grammar S→aSbS | bSaS | ε; construct all parse trees of abab and determine ambiguity.

## Solution

The root must use S→aSbS because the yield begins with a. Its explicit b can be the b at position 2 or position 4. These exhaust the possibilities. Use S[children] for an ordered parse-tree node; S[ε] is an empty production.

Tree 1: S[a, S[ε], b, S[a, S[ε], b, S[ε]]]
Tree 2: S[a, S[b, S[ε], a, S[ε]], b, S[ε]]

Accessible tree description: in tree 1 the root’s first S is empty and its final S generates ab. In tree 2 its first S generates ba and its final S is empty. Their leftmost derivations are:
S⇒aSbS⇒abS⇒abaSbS⇒ababS⇒abab.
S⇒aSbS⇒abSaSbS⇒abaSbS⇒ababS⇒abab.
The inner two-letter strings ab and ba each have only their direct production with both S children empty. Consequently there are precisely two trees, not merely at least two. Distinct trees with the same terminal yield prove ambiguity.
