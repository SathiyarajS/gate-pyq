**Type / marks:** MCQ, 1 mark(s).

**Official answer:** C

**Derived answer:** C

**Paraphrased problem context:** S1: The sequence of procedure calls is a preorder traversal of the activation tree. S2: The sequence of procedure returns is a postorder traversal. Which is correct? A S1 true/S2 false; B S1 false/S2 true; C both true; D both false.

## Solution

A procedure activation is entered before its child calls, producing preorder. It returns only after its nested calls finish, producing postorder. Thus both statements are true, C, in the ordinary sequential, properly nested call-return model.

For example, if main calls A, A calls B and C in order, and main then calls D, the entry order is main,A,B,C,D. The completion order is B,C,A,D,main. These are exactly preorder and postorder on the ordered activation tree. Recursive calls create distinct activation nodes even when the procedure name repeats; one must not merge all calls of the same procedure into a single node.

**Type / marks:** MCQ, 1 mark(s).

**Official answer:** C

**Derived answer:** C

**Paraphrased problem context:** S1: Every SLR(1) grammar is unambiguous, but some unambiguous grammars are not SLR(1). S2: For every context-free grammar there is a parser taking at most O(n³) time for an input of length n. Which is correct? A S1 true/S2 false; B S1 false/S2 true; C both true; D both false.

## Solution

A conflict-free SLR(1) table yields a unique parse, so every SLR(1) grammar is unambiguous. The converse fails: the standard grammar S→L=R|R, L→*R|id, R→L is unambiguous but has an SLR shift-reduce conflict. General CFG recognition and construction of a parse can be done in O(n³) for a fixed grammar, for example by Earley parsing or CYK after normalization. Thus both statements hold, C; this does not claim that exponentially many parse trees can all be listed in cubic time.

In the counterexample grammar, the LR(0) state after recognizing L contains S→L·=R and R→L·. Since '=' belongs to FOLLOW(R), SLR would both shift '=' and reduce R→L there. Thus unambiguity alone does not remove SLR conflicts. For cubic parsing, CYK stores whether each nonterminal derives each substring and considers O(n) split points for O(n²) substrings; the fixed grammar contributes only a constant factor. A parse witness can be recovered by stored backpointers.

**Paraphrased problem context:** A grammar and SDT are: P→D* E*; D→int ID records the identifier as int; D→bool ID records it as bool; E→E1+E2 checks E1.type=E2.type=int and sets E.type=int; E→!E1 checks E1.type=bool and sets E.type=bool; E→ID unconditionally sets E.type=int. Which claim holds? A correctly type-checks every syntactically correct program; B type-checks syntactically correct integer declarations and integer expressions; C type-checks syntactically correct boolean declarations and boolean expressions; D leads to an infinite loop.

## Solution

The ID expression action unconditionally sets its type to int instead of consulting the declarations. Consequently integer-only, properly declared expressions using + receive the intended types, but a declared boolean is still labeled int and a valid negation can be rejected. The finite semantic actions do not themselves loop. Thus B. As usual, the limited claim assumes the mentioned integer identifiers have valid declarations; the displayed action does not implement undeclared-variable checking.

Trace a valid boolean declaration/expression: bool flag; !flag. The declaration records bool, but E→ID labels flag as int; the negation action then demands bool and rejects a valid expression. Conversely int a; int b; a+b labels both operands int and passes. A corrected ID action would look up ID.lexeme in the symbol table, reject undeclared identifiers, and copy the declared type. Thus the exact defect is the unconditional int assignment, not the grammar's use of repetition.

**Paraphrased problem context:** For terminals {a,b,c,d,f}, grammar S→daT|Rf, T→aS|baT|ε, R→caTR|ε has a partially filled LL(1) table. Numbered cells are 1=(S,c), 2=(S,f), 3=(T,c), 4=(T,$). Known cells are (S,d)=S→daT; (T,a)=T→aS; (T,b)=T→baT; (T,f)=T→ε; (R,c)=R→caTR; (R,f)=R→ε; other unnumbered cells blank. Choose entries (1,2,3,4): A (S→Rf,S→Rf,T→ε,T→ε); B (blank,S→Rf,T→ε,T→ε); C (S→Rf,blank,blank,T→ε); D (blank,S→Rf,blank,blank).

## Solution

FIRST(R)={c,ε}, so FIRST(Rf)={c, f}; both numbered S-row cells contain S→Rf. From R→caTR, c belongs to FOLLOW(T), and nullable R carries FOLLOW(R)={f} into FOLLOW(T). From S→daT and T→aS, the start marker $ also reaches FOLLOW(T). Thus FOLLOW(T)={c, f,$}, and the numbered T-row cells at c and $ contain T→ε. Therefore A.

The FIRST rule puts A→α in every terminal column of FIRST(α) except ε. When α is nullable, put it in all FOLLOW(A) columns. For S→Rf, R can start with c or disappear, exposing f. For T→ε, the c column comes from T followed by R in R→caTR; the f column comes from the following nullable R and S→Rf; the end marker flows from start S through S→daT. No guessed table entry is needed once these sets are computed.

**Paraphrased problem context:** A compiler represents this basic block by a common-subexpression DAG: a=b+c; e=a+1; d=b+c; f=d+1; g=e+f;. How many DAG nodes are needed? The symbol in the additions to a and d is the constant digit 1.

## Solution

The code uses the constant 1, not a variable i. A common-subexpression DAG has three leaves b, c, 1. One addition node b+c is labeled by both a and d. A second addition node (b+c)+1 is labeled by both e and f. The final addition node adds that second node to itself and is labeled g. Hence there are 3 leaves plus 3 operation nodes, totaling 6. Variable labels are not separate DAG nodes in this representation.

Name the six nodes: n1=b, n2=c, n3=constant 1, n4=+(n1,n2) labeled a,d, n5=+(n4,n3) labeled e,f, n6=+(n5,n5) labeled g. The code does not change b or c, so the two b+c expressions really share one node. Repeated variable names attached as labels are not new values/nodes. This is common-subexpression DAG construction, not a syntax tree that duplicates every appearance or algebraic strength reduction to multiplication.

**Official answer:** D

**Derived answer:** D

**Paraphrased problem context:** Which is NOT an intermediate representation of source computation? A three-address code; B abstract syntax tree; C control-flow graph; D symbol table. Multiple selections are permitted.

## Solution

Three-address code, an abstract syntax tree, and a control-flow graph represent program computations or structure. A symbol table instead records information about names, types, scopes, and bindings. It supports analysis but is not an intermediate representation of the source computation. Thus D.

For an assignment x=a+b, three-address code records the operation, an AST records its expression structure, and a CFG records possible control transfers around it. The symbol table instead stores facts such as x's declared type or scope. A compiler may use all four structures; “used by a compiler” is broader than “intermediate representation.”

**Official answer:** A

**Derived answer:** A

**Paraphrased problem context:** USE(S) means variables used in S; IN(S),OUT(S) are live variables on entry/exit. Basic block is S1 followed by S2. A OUT(S1)=IN(S2); B OUT(S1)=IN(S1)∪USE(S1); C OUT(S1)=IN(S2)∪OUT(S2); D OUT(S1)=USE(S1)∪IN(S2).

## Solution

Inside a basic block S1 has S2 as its unique immediate successor. Values live just after S1 are exactly those live just before S2, so OUT(S1)=IN(S2), A. Uses at S1 do not automatically remain live afterward, and a definition in S2 can kill a value that is live after S2.

The general equations are OUT(S)=union of IN of immediate successors, and IN(S)=USE(S)∪(OUT(S)−DEF(S)). A basic block has no branch between S1 and S2, reducing the first equation to A. For example S1 reads x then S2 overwrites x: x can be used at S1 without needing to remain live after it, refuting formulas that force USE(S1) into OUT(S1).

## Solution

On reading < from the initial closure the kernel is S→<·S>. Its closure adds all seven S productions with the dot at the beginning: S→·S#cS, ·SS, ·S@, ·<S>, ·a, ·b, ·c. Reading a second < reproduces exactly the same kernel and closure. Thus GOTO(GOTO(I0,<),<) has 1+7=8 items; the augmented S-prime item is not added because closure expands only S.

The resulting item set is {S→<·S>, S→·S#cS, S→·SS, S→·S@, S→·<S>, S→·a, S→·b, S→·c}. Recursive closure does not create infinitely many copies: items are set members. In particular, productions beginning with S are added once and their expansion adds no new productions beyond the seven already present.
