**Type / marks:** fill-in, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** 2 registers and 6 input reads, excluding final result storage

**Essential problem context (paraphrased):** Evaluate (a+b)*c−d/e**f on a two-address machine whose operands may be registers or memory. Minimize operand memory accesses and give the required registers. ** denotes exponentiation.

## Solution

Assume six independent input values initially reside in memory, arithmetic allows a memory source and register destination, and exponentiation is an available operation. Read e into R1 and compute R1:=R1**f; read d into R2 and compute R2:=R2/R1. Reuse R1 for a, then add b and multiply by c; finish R1:=R1−R2. Each of a, b, c, d, e, f is read once, achieving the six-read lower bound. Two registers retain one partial result while forming the other; one register would require a spill or destructive memory temporary and extra traffic. A required final output store adds one access; instruction fetches are not operand accesses.

**Essential problem context (paraphrased):** A link editor matches external names to definitions in other modules, macro arguments to parameters, subroutine parameters to arguments, or serves as an editor/compiler user interface?

## Solution

Separately compiled modules contain symbol definitions and unresolved references to symbols defined elsewhere. The linker combines modules, locates matching definitions, assigns final locations and adjusts references or relocation records. This is the external-name matching described by B. Macro-parameter substitution belongs to macro expansion, and runtime argument passing or compiler checking handles subroutine parameters. The tool’s name does not mean it is an interactive bridge to a text editor. Dynamic linking can defer some resolution, but the semantic task remains symbol binding across modules.

**Essential problem context (paraphrased):** Assess A recursive descent cannot handle left recursion; B postfix is best for optimization; C without recursion/pointers dynamic allocation is unnecessary; D C can simulate call-by-name; E no Pascal feature violates strong typing.

Historical Pascal variant records can bypass type discipline, refuting E. C is sometimes intended under a restricted static-allocation language model, but that restriction is not stated.

**Official answer:** Not available; no official key located.

**Independently derived answer:** x=1, z=100.

**Essential problem context (paraphrased):** All variables are integers. Procedure P(a,b,c) executes a:=2; c:=a+b. Main executes x:=1; y:=5; z:=100; P(x,x*y,z); write(x,z). Determine the output for call by value.

## Solution

With call by value, evaluate the actual arguments in the caller before entering P: x yields 1, x*y yields 5, and z yields 100. Allocate independent local formals with values (a,b,c)=(1,5,100).

The assignment a:=2 changes only the local a. Next c:=a+b computes 2+5=7 and places it in the local c. Neither assignment targets the caller’s variables, so after return x remains 1, y remains 5, and z remains 100. The main program prints x=1,z=100.

The intermediate c=7 is not the value printed by the program: the print is outside P and names z. Ordinary call by value has no copy-out stage. Adding copy-out would change the parameter mechanism to value-result, which is a different question. Evaluating the expression x*y once at the call is crucial for distinguishing this case from call by name.

# GATE 1991: Q49 (printed B Q9(a.ii))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204230/GATE1991.pdf#page=6), physical page 6. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, Unallocated leaf; group total 10 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Strict reference-only actuals: invalid call, no defined output. If expression actuals are materialized in a temporary: x=2,z=7.

**Essential problem context (paraphrased):** All variables are integers. Procedure P(a,b,c) executes a:=2; c:=a+b. Main executes x:=1; y:=5; z:=100; P(x,x*y,z); write(x,z). Determine the output for call by reference, stating any validity assumption.

## Solution

Pure call by reference binds each formal to an assignable storage location. The actuals x and z have such locations, but x*y is an arithmetic expression and has no variable location to which a conventional reference formal can bind. Thus in a language requiring variable actuals for reference parameters, this call is rejected and there is no output. This is an important qualification to the otherwise familiar textbook calculation.

If the intended pseudo-language permits an expression actual by evaluating it into a temporary, evaluate x*y=1·5=5 at call entry and bind b to that temporary. Bind a directly to x and c directly to z. Executing a:=2 sets x to 2. The temporary b remains 5; it is not a live expression. Then c:=a+b sets z=2+5=7. On return the program prints x=2,z=7.

The temporary convention is sufficient here because P never assigns to b. It is nevertheless an additional semantic rule, not inherent in reference passing. In particular, re-evaluating x*y after changing x would give 10 and would implement call by name rather than this temporary-backed reference convention.

**Independently derived answer:** x=2,z=12.

**Essential problem context (paraphrased):** All variables are integers. Procedure P(a,b,c) executes a:=2; c:=a+b. Main executes x:=1; y:=5; z:=100; P(x,x*y,z); write(x,z). Determine the output for call by name.

## Solution

Call by name delays evaluation of an actual argument until its formal is used, in the caller’s environment. Think of a as a getter/setter for x, b as a thunk returning x*y, and c as a getter/setter for z. The caller’s x and y, not unrelated locals inside P, are the names captured by b’s thunk.

The first statement a:=2 follows the location associated with x and changes x from 1 to 2. The next statement c:=a+b first obtains a=2 and evaluates b’s expression using the current caller state: x*y=2·5=10. It therefore writes 12 through c into z. After return, main prints x=2,z=12.

A textual substitution illustrates this particular collision-free example: x:=2; z:=x+x*y. General call-by-name implementations must preserve environments and avoid accidental name capture, so literal substitution is only an explanatory model. The difference from temporary-backed reference passing is that b is not frozen at its original value 5. The nonassignability of x*y does not prevent this example’s by-name use because b is only read, never assigned.

**Official answer:** Not available; no official key located.

**Independently derived answer:** a=5,b=10.

**Essential problem context (paraphrased):** Global integers a,b; procedure P sets a:=5;b:=10. Procedure Q declares its own local integers a,b and calls P. Main sets global a:=1;b:=2, calls Q, then prints global a,b. Give output under static scope.

## Solution

Under static, or lexical, scope, a nonlocal name is resolved by the source program’s nesting structure. P is declared at global level, alongside Q, rather than inside Q. The closest enclosing declarations for the a and b used in P are therefore the global variables.

Main first assigns those global variables (1,2). Q then creates a fresh activation containing its own local a,b. Although Q calls P, Q’s locals are not lexically enclosing declarations of P. P’s assignments update the globals to (5,10), leaving Q’s locals untouched. Q returns and its activation disappears. Main then prints the global values a=5,b=10.

A useful implementation view is that P’s static link identifies the global environment, independent of which procedure called it. The existence of same-spelled variables in the caller does not change this link. Their uninitialized values are irrelevant because P never reads or writes them under static scoping.

**Official answer:** Not available; no official key located.

**Independently derived answer:** a=1,b=2.

**Essential problem context (paraphrased):** Global integers a,b; procedure P sets a:=5;b:=10. Procedure Q declares its own local integers a,b and calls P. Main sets global a:=1;b:=2, calls Q, then prints global a,b. Give output under dynamic scope.

## Solution

Dynamic scope resolves a free name by searching the active call chain from the current activation outward. During P, the chain is P→Q→main/global. P has no local a or b; the nearest active bindings are Q’s local a,b. Hence P’s assignments set Q’s variables to (5,10), rather than modifying the globals.

The globals were initialized to (1,2) by main and are still (1,2) when Q returns. Q’s locals disappear with its activation, and the final print in main uses the globals. The output is a=1,b=2.

No undefined read is caused by Q’s initially uninitialized locals: P overwrites them before they could be read, and the final print occurs after they are out of scope. Dynamic scoping must not be confused with dynamic memory allocation or call-by-reference parameter passing. It is a rule for selecting which binding an identifier denotes; the assignment operation itself is unchanged.

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204230/GATE1991.pdf#page=7), physical page 7. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Unambiguous; / has higher precedence than −, and each operator is parsed left-associatively.

**Essential problem context (paraphrased):** For arithmetic expressions using binary, mathematically nonassociative operators minus and division, the start symbol is E and the grammar is E→E−T | T; T→T/F | F; F→(E) | id. Is it unambiguous? If so state relative precedence; otherwise provide an unambiguous grammar giving division higher precedence.

## Solution

The grammar separates expression levels: E combines terms with minus, while T combines factors with division. Thus id−id/id parses as id−(id/id), never as (id−id)/id. Division has higher precedence than subtraction.

Both recursive productions are left-recursive, so unparenthesized chains group to the left. For example id−id−id has structure (id−id)−id, and id/id/id has structure (id/id)/id. This is a syntactic associativity convention; it does not claim the arithmetic operators obey an associative law.

For uniqueness, consider an expression outside its matched parentheses. If it has a top-level minus, the root must be E→E−T, split at its last such minus because T cannot contain an unparenthesized minus. If there is no such minus, use E→T. Similarly a top-level slash in a term forces T→T/F split at its last top-level slash, since F cannot contain an unparenthesized slash. At the factor level, either the token is id or the uniquely matched outer parentheses contain an expression, to which the same argument applies. Induction on expression length gives a unique parse. Redundant parentheses are allowed by the grammar, but do not create two parses for the same token string.

**Essential problem context (paraphrased):** For arithmetic expressions using binary, mathematically nonassociative operators minus and division, the start symbol is E and the grammar is E→E−T | T; T→T/F | F; F→(E) | id. Does it permit redundant parentheses such as (id/id) and id−(id/id)? Modify it to eliminate redundant parentheses, making minimal changes and adding at most one production rule.

## Solution

The original grammar allows both examples through F→(E). Deleting parentheses must be judged by preservation of the parse tree under / precedence and left associativity, not accidental numerical identities for particular values. Parentheses are needed around a subtraction in either operand of division, around a division in the right operand of division, and around a subtraction in the right operand of subtraction. They are not needed around a whole expression, a single id, a left operand at equal precedence, or a division used as a subtraction operand.

Use the following four-nonterminal grammar:
E→T | S
S→E−T | E−(S)
T→id | T/F | (S)/F
F→id | (S) | (T/F) | ((S)/F)

S is exactly subtraction-rooted, while T/F and (S)/F together are exactly division-rooted. This grammar generates every binary expression tree with no removable parenthesis pair. F appears only after /, preventing redundant outer parentheses. Examples: it generates id−(id−(id−id)) and id/((id−id)/id), but rejects (id/id), id−(id/id), (id), and ((id−id))/id. The source’s “one more production rule” is interpreted in the common sense of one more nonterminal production group: only S is added to E,T,F. All three original groups must change to prevent the old whole-expression wrapping while preserving needed contexts. A global minimum in number of RHS alternatives is not claimed because the source does not define its edit metric.

**Official answer:** Not available; no official key located.

**Independently derived answer:** E→TR; R→−TR|−(S)R|ε; S→T−TR|T−(S)R; T→idU|(S)/FU; U→/FU|ε; F→id|(S)|(T/F)|((S)/F).

**Essential problem context (paraphrased):** For arithmetic expressions using binary, mathematically nonassociative operators minus and division, the start symbol is E and the grammar is E→E−T | T; T→T/F | F; F→(E) | id. Part (b) requires necessary-parentheses-only expressions. For the grammar E→T|S; S→E−T|E−(S); T→id|T/F|(S)/F; F→id|(S)|(T/F)|((S)/F), remove left recursion.

## Solution

First notice the indirect cycle E→S→E−T or E−(S). Removing only the obvious T→T/F recursion is insufficient. Substitute S’s alternatives into E to obtain E→T | E−T | E−(S). Its recursive suffixes are −T and −(S); its base is T. Introduce a tail R:
E→T R
R→−T R | −(S) R | ε.

S must still mean a subtraction-rooted expression, not an arbitrary E. Substituting E=T R into S initially gives S→T R−T | T R−(S). This is valid, but an equivalent clearer form selects the first subtraction and then any remaining subtraction tail:
S→T−T R | T−(S) R.
Both describe a T followed by a nonempty sequence of subtraction suffixes. Their ordering is preserved; the rewrite is about syntax, not commuting arithmetic operations.

Remove T’s immediate recursion T→T/F | id | (S)/F using a new tail U:
T→id U | (S)/F U
U→/F U | ε.
Keep F→id | (S) | (T/F) | ((S)/F).

The complete grammar is the six displayed groups E,R,S,T,U,F. Every nonempty derivation of T begins with id or “(”. E and S begin through T; F directly begins with id or “(”; R begins with “−” or ε, and U with “/” or ε. No nonterminal can derive itself as the leftmost symbol, so neither direct nor indirect left recursion remains. The language is unchanged by the standard tail transformation. When constructing semantic actions, fold each R or U sequence leftward to retain the original left-associative parse: right-recursive grammar tails must not accidentally change subtraction or division evaluation order. The at-most-one-extra-production restriction belongs to part (b); part (c) requires the additional tail nonterminals.
