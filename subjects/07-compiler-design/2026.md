**Original question:** [Complete wording, options and figures](https://gate2026.iitg.ac.in/doc/download/2026/QPs/CS1.pdf#page=21).

**Paraphrased problem context:** Three declarations are considered: S1 begins char *str1 = "Hello; without a closing double quote; S2 is char *str2 = "Hello;"; and S3 is int *str3 = "Hello";. The options classify S1/S2 as lexical or syntactic errors and S3 as syntactic or semantic.

**Type / marks:** MSQ, 1.

**Official answer:** C

**Derived answer:** C

## Solution

Givens and goal
Three declarations are considered: S1 begins char *str1 = "Hello; without a closing double quote; S2 is char *str2 = "Hello;"; and S3 is int *str3 = "Hello";. The options classify S1/S2 as lexical or syntactic errors and S3 as syntactic or semantic.

Approach
Check whether valid tokens can be formed first, then whether the token sequence is grammatical, then whether the types are compatible.

Step-by-step solution
1. S1 opens a string literal but does not close it before the end of the line. Tokenization cannot form a valid string-literal token. In the compiler-phase classification used by the question, this is a lexical error.
2. S2 contains a properly closed string. Its semicolon inside the quotation marks is part of the string data, while the semicolon outside terminates the declaration. There is no lexical or syntactic error merely because both semicolons appear.
3. S3 has the shape of a grammatical declaration, but initializes an int pointer with a string literal, whose ordinary expression conversion produces a char pointer. The incompatible pointer types violate the C initialization constraints. This is a type/semantic error in the question's classification.
4. Therefore C correctly pairs the lexical error in S1 with the semantic error in S3. A and B misclassify S2, and D assigns the wrong compiler phase to S1.

**Precision caveat:** Real compilers may emit several cascading diagnostics after the malformed string. This solution classifies the primary defect, rather than treating every emitted diagnostic as a separate intended answer. In C, accepting a program after a warning or as an extension does not make a constraint violation valid standard C.

Phase distinction: lexical analysis groups characters into tokens, syntax checks token arrangements against the grammar, and semantic analysis checks constraints such as types. A semicolon character inside a valid string token has no role as a declaration terminator. That is why S2’s internal semicolon cannot by itself create a syntax error.

**Original question:** [Complete wording, options and figures](https://gate2026.iitg.ac.in/doc/download/2026/QPs/CS1.pdf#page=21).

**Paraphrased problem context:** Assess four claims: A LL(1) parsers backtrack; B an LL(1) grammar must be left-recursive; C an LL(1) grammar must be left-factored; D LL(1) parsers are more powerful than SLR parsers. The official choice is C, with a retained qualification about literal syntactic left factoring.

**Type / marks:** MSQ, 1.

**Official answer:** C

**Derived answer:** Official scoring answer C; literal necessity claim is overbroad (see discrepancy).

## Solution

Givens and goal
Assess four claims: A LL(1) parsers backtrack; B an LL(1) grammar must be left-recursive; C an LL(1) grammar must be left-factored; D LL(1) parsers are more powerful than SLR parsers. The official choice is C, with a retained qualification about literal syntactic left factoring.

Approach
Apply predictive-table conditions rather than treating grammar-transformation advice as an unrestricted necessity theorem.

Step-by-step solution
1. LL(1) selects a production from the next input token using a predictive parsing table. It does not use trial-and-error backtracking, so A is false.
2. Left recursion prevents ordinary predictive top-down parsing; it is something to remove, not a requirement for LL(1). Hence B is false.
3. Left factoring is a standard transformation for removing shared prefixes that obstruct predictive selection. This explains the intended textbook answer C, but syntactic left factoring is not literally necessary for every LL(1) grammar. Left factoring is also not sufficient: FIRST/FIRST or FIRST/FOLLOW conflicts can remain.
4. LL(1) does not have greater grammar-recognition power than SLR parsing. Thus D is false.

**Discrepancy / interpretation issue:** A reduced, productive counterexample is S → A a | A b, A → ε. The two S alternatives share the syntactic prefix A, so the grammar is not literally left-factored. Nevertheless FIRST(Aa)={a} and FIRST(Ab)={b}; the predictive table selects the two S productions in different columns. For A, its sole epsilon production is selected on FOLLOW(A)={a,b}. There are no conflicts, so the grammar is LL(1). Thus the exact general necessity claim in C is false under the standard syntactic definition of left-factored form. C remains the official scoring answer, but its literal necessity claim requires the qualification above. The issue is not restricted to unreachable or unproductive grammar alternatives.

**Review:** This counterexample was supplied during independent peer review and checked against FIRST/FOLLOW construction.

Predictive-table check for the counterexample:

    Nonterminal   lookahead a      lookahead b
    S             S→Aa             S→Ab
    A             A→ε              A→ε

Each table cell contains at most one production, despite the common written prefix A. For the “more powerful” claim, note also that SLR parsing can handle standard left-recursive grammars such as E→E+a | a, which this predictive LL(1) form cannot parse without transformation. Do not replace the LL(1) table condition with either “left-recursive” or “left-factored” as a complete characterization.

**Original question:** [Complete wording, options and figures](https://gate2026.iitg.ac.in/doc/download/2026/QPs/CS1.pdf#page=31).

**Paraphrased problem context:** The flow is Entry→B1→either B2 or B3→B4→B5→Exit. B1: a=b+i. B2: a=g*k; f=a−f; a=c*4. B3: t=g*k; b=c+m. B4: x=g*k; y=b+i. B5: z=c+m. All variables are integers. Find the redundant expression sets in B4 and B5.

**Type / marks:** MCQ, 2.

**Official answer:** D

**Derived answer:** D

## Solution

Givens and goal
The flow is Entry→B1→either B2 or B3→B4→B5→Exit. B1: a=b+i. B2: a=g*k; f=a−f; a=c*4. B3: t=g*k; b=c+m. B4: x=g*k; y=b+i. B5: z=c+m. All variables are integers. Find the redundant expression sets in B4 and B5.

Approach
An expression is available only if it has already been computed on every incoming path and neither operand has been reassigned since.

Step-by-step solution
1. The control-flow shape is a diamond followed by a tail:

    B1 ──→ B2 ──┐
      └──→ B3 ──┴──→ B4 ──→ B5

At the B4 merge, availability uses the intersection of the incoming expression sets, not their union.
2. B1 computes b+i. Along B2 neither b nor i is assigned, so this expression remains available there. Along B3, however, b is overwritten by c+m. That kills the old b+i value. Hence b+i is not available on every path to B4 and y=b+i is not globally redundant.
3. Both B2 and B3 compute g*k, and neither subsequently changes g or k. Thus g*k is available along both incoming paths. Its evaluation in x=g*k is redundant. B2 later overwrites a, but that changes the destination holding a previous result, not the operands g and k; a transformation may preserve the value in a temporary.
4. B3 computes c+m, but B2 does not. B4 computes neither c+m nor anything proving its value was previously computed on the B2 path. Therefore z=c+m in B5 is not redundant on all paths.
5. The required sets are B4:{g*k}, B5:empty, option D. Option A wrongly keeps b+i; B wrongly treats a computation on only one branch as universally available; C also incorrectly keeps b+i.

The original block labels, edges and assignment targets were visually checked. In particular a=c*4 assigns a, not c; the target variable matters when deciding whether an expression is killed.

**Original question:** [Complete wording, options and figures](https://gate2026.iitg.ac.in/doc/download/2026/QPs/CS1.pdf#page=41).

**Paraphrased problem context:** G1 has D→TV, T→int|float, V→V₁ id|id; G2 has D→D₁ id|T id, T→int|float. In SDD1, T.type is set by its keyword, D.type=T.type, V.type=T.type, V₁.type=V.type, and each id is entered with V.type. In SDD2, D.type comes from D₁.type or T.type and each id is entered with that child’s type. Decide A same language, B SDD2 S-attributed, C SDD1 L-attributed with only inherited attributes, D same symbol-table entries.

**Type / marks:** MSQ, 2.

**Official answer:** A;B;D

**Derived answer:** A;B;D

## Solution

Givens and goal
G1 has D→TV, T→int|float, V→V₁ id|id; G2 has D→D₁ id|T id, T→int|float. In SDD1, T.type is set by its keyword, D.type=T.type, V.type=T.type, V₁.type=V.type, and each id is entered with V.type. In SDD2, D.type comes from D₁.type or T.type and each id is entered with that child’s type. Decide A same language, B SDD2 S-attributed, C SDD1 L-attributed with only inherited attributes, D same symbol-table entries.

Approach
Compare generated token sequences separately from how attribute values flow through each parse tree.

Step-by-step solution
1. Both grammars generate a type keyword, either int or float, followed by one or more identifier tokens. G1 builds an identifier list through V; G2 builds the same sequence by extending D. Therefore their languages are identical, establishing A.
2. In SDD2, T.type comes from a type keyword and D.type comes from a child T or D. Every attribute value flows upward from children to the left-hand-side symbol, or is a constant. All attributes are synthesized, so SDD2 is S-attributed and B is true.
3. SDD1 passes the type inherited by V down through the identifier list. But it also contains synthesized attributes, including T.type and D.type. Its inherited dependencies are L-attributed, yet the stronger wording that it contains only inherited attributes is false. Thus C is false.
4. In either definition, every identifier receives the same type supplied by the leading keyword. Thus the same identifier/type entries are recorded, establishing D. The ways in which the values flow through the parse tree differ; the resulting entries do not.

**Common error:** L-attributed does not mean exclusively inherited. An L-attributed definition can contain synthesized attributes as well.

Example: for the token sequence int id₁ id₂, SDD1 obtains int from T and passes it down through V to both identifiers. SDD2 first constructs the declaration for int id₁, synthesizes its type upward, and uses that type when extending the declaration with id₂. Both call put with (id₁,int) and (id₂,int). In SDD1, the existence of the inherited V.type does not erase the synthesized T.type and D.type; that is the exact overstatement in C.

## Solution

Givens and goal
Identifiers are letter(letter|digit)*; numbers are digit+; whitespace is ignored. Letters are A-Z or a-z. Tokenize x1 23mm 78 y 7z zz5 14A 8H AaYcD and count non-whitespace tokens.

Approach
At each position take the longest prefix matching a token definition.

Step-by-step solution
1. A letter-starting run can include later digits, so x1, zz5, and AaYcD are each a single identifier. A digit-starting run cannot be an identifier because the initial-letter condition fails.
2. Consequently 23mm splits as number 23 then identifier mm; 7z splits as 7 and z; 14A splits as 14 and A; 8H splits as 8 and H. Whitespace is a separator but is not required at every token boundary.
3. The full sequence is x1 | 23 | mm | 78 | y | 7 | z | zz5 | 14 | A | 8 | H | AaYcD. Numbering these items gives 13 non-whitespace tokens.
4. Equivalently the nine whitespace-separated chunks contribute 1+2+1+1+2+1+2+2+1=13. The answer follows the specified lexer definitions, not any additional rules a particular programming language might impose on malformed numeric literals.

**Paraphrased problem context:** Use canonical LR(0) parsing for S→ACB, A→aA|ε, C→cC|ε, B→bB|b, with start S. Count shift-reduce conflicts in the ACTION table: A 2; B 3; C 4; D 5.

## Solution

Givens and goal
Use canonical LR(0) parsing for S→ACB, A→aA|ε, C→cC|ε, B→bB|b, with start S. Count shift-reduce conflicts in the ACTION table: A 2; B 3; C 4; D 5.

Approach
Construct the relevant item closures and identify states containing both a shift and a completed item.

Step-by-step solution
1. Augment with S′→S. A completed LR(0) item X→α· requests a reduction on every terminal, without restricting it to FOLLOW(X). It conflicts with any terminal shift present in the same state.
2. The initial state contains S′→·S, S→·ACB, A→·aA, A→·. It shifts a and reduces A→ε, giving one conflicting ACTION cell on a. After shifting a, the state contains A→a·A and the same two A closure items, giving a second conflict on a.
3. After recognizing A, the state contains S→A·CB, C→·cC, C→·. It shifts c and reduces C→ε, giving one conflict on c. After shifting c, the state contains C→c·C with the same C closure items, giving another conflict on c.
4. After recognizing AC, the B closure has B→·bB and B→·b. Shifting b reaches {B→b·B, B→b·, B→·bB, B→·b}. This state shifts b and reduces B→b, giving the fifth conflict.
5. The remaining completed states contain only S′→S·, A→aA·, C→cC·, S→ACB·, or B→bB·; they have no terminal shift. The state before reading B also has no completed item. These account for all 11 canonical states.
6. Therefore there are exactly five conflicting cells, D. Using SLR FOLLOW restrictions instead would be a different parsing method and could change which conflicts remain.

**Type / marks:** MCQ, 2 mark(s).

**Official answer:** A

**Derived answer:** A

**Paraphrased problem context:** Blocks execute B1: a=b+c; B2: d=a+e; B3: e=a+f; B4: g=d+e. Edges are entry→B1, B1→B2, B1→B3, B2→B4, B3→B1, B4→exit. No variable is live after exit. Candidate exit sets (B1,B2,B3,B4) are A ({a,b,c,e,f},{d,e},{b,c,e,f},∅); B (∅,{d,e},{a,c,f},∅); C ({a,b,c,e,f},{d,e},{c,e,f},∅); D (∅,{d,e,f},{a,b,c,e,f},∅).

## Solution

Givens and goal
Blocks execute B1: a=b+c; B2: d=a+e; B3: e=a+f; B4: g=d+e. Edges are entry→B1, B1→B2, B1→B3, B2→B4, B3→B1, B4→exit. No variable is live after exit. Candidate exit sets (B1,B2,B3,B4) are A ({a,b,c,e,f},{d,e},{b,c,e,f},∅); B (∅,{d,e},{a,c,f},∅); C ({a,b,c,e,f},{d,e},{c,e,f},∅); D (∅,{d,e,f},{a,b,c,e,f},∅).

Approach
Solve backward liveness equations to a fixed point, including the loop edge.

Step-by-step solution
1. For each block, OUT is the union of successor IN sets; IN=USE∪(OUT−DEF). Here USE/DEF are B1:{b,c}/{a}, B2:{a,e}/{d}, B3:{a,f}/{e}, and B4:{d,e}/{g}.
2. OUT4=∅, so IN4={d,e}. Hence OUT2={d,e} and IN2={a,e}∪({d,e}−{d})={a,e}.
3. The loop equations are OUT3=IN1, IN3={a,f}∪(IN1−{e}), OUT1=IN2∪IN3, and IN1={b,c}∪(OUT1−{a}). Starting empty and propagating produces the least fixed point IN1={b,c,e,f} and IN3={a,b,c,f}.
4. Substitute back to check: OUT1={a,e}∪{a,b,c,f}={a,b,c,e,f}; removing a and adding b,c indeed gives IN1={b,c,e,f}. OUT3=IN1={b,c,e,f}; removing e and adding a,f indeed gives IN3={a,b,c,f}.
5. The requested exit sets are therefore OUT1={a,b,c,e,f}, OUT2={d,e}, OUT3={b,c,e,f}, OUT4=∅, matching A. In particular b stays live through B3 because the loop can return to B1 and read b before any redefinition.
6. The source assignments and all arrows were inspected visually. Ignoring the back edge would incorrectly remove values needed on a later loop iteration.
