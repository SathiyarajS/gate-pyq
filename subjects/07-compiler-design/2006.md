**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203119/GATE2006.pdf#page=1), physical page 1. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** MCQ, 1 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** D

## Solution

The state after recognizing S* contains S→S*·E plus closure items E→·F+E,E→·F,F→·id. The item E→F·+E occurs after a transition on F, together with E→F·. The item E→F+·E occurs after a further transition on +, again with the initial E/F closure. These three kernels are different states; closure does not introduce either of the other listed advanced items. Thus none of the listed pairs coexist, D.

**Official answer:** Not available; no official key located.

**Independently derived answer:** A

## Solution

work1 reads a[i+2], writes a[j], then reads a[i+2] again in its return expression. work2 saves the first value and reuses it after the store. If j=i+2, the store changes the location that work1 rereads, so the functions need not return the same value; S1 is false. Compiler transformations also do not universally improve runtime on every target/input, and this transformation is not even semantics-preserving without a non-alias condition. S2 is false. Thus A. The clearer GateForum code confirms a[j]=x+1 and return a[i+2]−3 versus the saved-value return t2−3. For i=0, j=2, initial a[2]=5, work1 returns 3 whereas work2 returns 2.

**Type / marks:** MCQ, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** B

## Solution

Initially ia=3 and ib=8; the expression ib+5 evaluates to 13. Under the stated expression-to-temporary reference model, the compiler passes the address of a temporary containing 13, not the address of ib. swap sets ia to 13 and the temporary to 3; ib remains 8. S1 and S4 hold, so B. This is the pedagogical model specified by the options, not a guarantee that every actual FORTRAN standard/compiler permits defining an expression-associated dummy argument.

**Official answer:** Not available; no official key located.

**Independently derived answer:** D

## Solution

S→ER and R→*E{print(*)}R|ε put multiplication below the expression E; E→F+E{print(+)}|F groups the addition on the right. For 2*3+4, first print 2, then parse E for 3+4, printing 3,4,+, then print * when that E finishes. The output is 234+*, option D. Applying ordinary arithmetic precedence would incorrectly give 23*4+.

**Independently derived answer:** D

## Solution

Within the inner j loop, i%2 and 5*i are invariant. The expression 4*j occurs in both updates and can be shared. The products by loop indices can use strength reduction through induction-variable increments. However x and y are updated and may be used later; nothing in the snippet establishes that those results are dead. Therefore the claim of available dead-code elimination is unsupported and is the intended false statement, D. This uses the ordinary compiler-question assumption that program behavior is defined and x,y remain live afterward.
