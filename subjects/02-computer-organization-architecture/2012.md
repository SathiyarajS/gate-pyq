**Paraphrased problem context:** The decimal value 0.5 in IEEE single precision floating point representation has
        (A) fraction bits of 000…000 and exponent value of 0
        (B) fraction bits of 000…000 and exponent value of −1
        (C) fraction bits of 100…000 and exponent value of 0
        (D) no exact representation

## Solution

Normalize 0.5 as 1.0₂×2^(−1). The fractional field after the implicit leading 1 is all zeros; the actual unbiased exponent is −1. Thus B uses the mathematical exponent convention. For clarity, the stored biased exponent is −1+127=126, binary 01111110, and the full 32-bit encoding is 0x3F000000. The exponent field itself is not a signed −1.

Worked check / additional reasoning: The single-precision format has one sign bit, eight exponent bits, and 23 stored fraction bits. Here the sign is 0, the exponent field is 01111110, and every fraction bit is 0; binary fractions with denominator a power of two can be exact.

**Paraphrased problem context:** Register renaming is done in pipelined processors
        (A) as an alternative to register allocation at compile time
        (B) for efficient access to function parameters and local variables
        (C) to handle certain kinds of hazards
        (D) as part of address translation

## Solution

Renaming assigns different physical registers to distinct logical-register definitions. This removes false dependencies due to reusing a register name, specifically WAR and WAW hazards, allowing more overlapping execution. It cannot remove a genuine RAW data dependency. Thus it handles certain pipeline hazards, C.

Worked check / additional reasoning: For example, an older instruction reading logical R1 and a newer instruction writing logical R1 need not share a physical register. Giving the newer result a new physical destination avoids a write-after-read name hazard while preserving the old value for its reader.

**Paraphrased problem context:** A 256 KByte, four-way set-associative write-back cache uses 32-byte blocks and 32-bit byte addresses. Every tag-directory entry holds the tag plus 2 valid bits, 1 modified bit, and 1 replacement bit.
How many address tag bits are there?
(A) 11 (B) 14 (C) 16 (D) 27.

## Solution

Using binary cache units, 256 KiB/32 bytes=8192 cache lines. Four lines per set give 2048=2¹¹ sets, so the set index uses 11 bits. A 32-byte block requires 5 byte-offset bits. The remaining address bits are tag bits: 32−11−5=16, C.

Worked check / additional reasoning: The address splits as [16 tag bits | 11 set bits | 5 byte-offset bits]. Associativity reduces the number of sets relative to the number of lines, so using 13 line-index bits would incorrectly treat the cache as direct mapped.

**Paraphrased problem context:** A 256 KByte, four-way set-associative write-back cache uses 32-byte blocks and 32-bit byte addresses. Every tag-directory entry holds the tag plus 2 valid bits, 1 modified bit, and 1 replacement bit.
What is the tag-directory size?
(A) 160 Kbits (B) 136 Kbits (C) 40 Kbits (D) 32 Kbits.

## Solution

There are 256×1024/32=8192 cache lines and hence 8192 tag-directory entries. The preceding calculation gives a 16-bit address tag. Each entry additionally has the explicitly specified 2 valid bits, 1 modified bit and 1 replacement bit, for 16+2+1+1=20 bits. The directory is 8192×20=163, 840 bits=160 Kibits, option A (printed as Kbits). Count entries per cache line, not per set; the problem explicitly assigns the replacement bit per entry.

Worked check / additional reasoning: Four ways do not mean only one tag per set: each way stores a distinct block and needs its own tag and metadata. Equivalently, 2048 sets×4 entries/set×20 bits/entry=163840 bits, confirming the per-line calculation.
