

# GATE 1995: Q87 (printed B Q26(a))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204046/GATE1995.pdf#page=8), physical page 8. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 3 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Candidate keys AB and BC make all attributes prime. C→A satisfies3NF but violates BCNF since C is not a superkey.

**Essential problem context (paraphrased):** For R(A,B,C) with functional dependencies AB→C and C→A, show that R is in3NF but not BCNF.

## Solution

Compute enough closures to identify the keys. (AB)+ contains A,B and gains C by AB→C, so AB is a superkey; neither A nor B alone determines all attributes, so it is minimal. (BC)+ gains A by C→A and is likewise a candidate key. Every candidate key must contain B because no dependency can introduce B. A key containing B must also include A or C, giving precisely AB and BC. Thus A,B,C are all prime attributes, meaning each occurs in at least one candidate key.

For 3NF, every nontrivial dependency X→Y with a single right-side attribute must have X a superkey or Y prime. The given AB→C has a superkey determinant. In C→A, C is not a superkey, but A is prime because it belongs to key AB. This is allowed in3NF. In fact every attribute of R is prime, so any implied single-attribute dependency also meets that alternative of the definition. Hence R is in3NF.

BCNF removes the prime-attribute exception: every nontrivial dependency must have a superkey on the left. Here C+={C,A}; it cannot acquire B, so C is not a superkey. The nontrivial dependency C→A therefore violates BCNF. Being in3NF does not imply that every determinant is a key. This conclusion assumes the displayed dependencies generate the schema's constraints and that the relation is in first normal form, as is conventional for this normalization problem.

# GATE 1995: Q88 (printed B Q26(b))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204046/GATE1995.pdf#page=8), physical page 8. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, Unallocated leaf; group total 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** AB and BC are exactly the candidate keys.

**Essential problem context (paraphrased):** For R(A,B,C), with AB→C and C→A, determine every minimal key.

## Solution

A candidate key must determine all three attributes, and none of its proper subsets may do so. Since B does not occur on the right side of either given functional dependency, starting from attributes that omit B can never derive B. Thus every key must contain B. The closure B+ is just {B}, so B by itself is not enough.

Add A: (AB)+ initially contains A,B and then AB→C adds C, so AB is a superkey. Removing A leaves B+, which lacks A,C; removing B leaves A+={A}. Therefore AB is minimal. Add C instead: (BC)+ contains B,C, then C→A adds A, so BC is a superkey. Removing B leaves C+={C,A}, and removing C leaves B+={B}; neither is all of R. Thus BC is minimal.

These are exhaustive. Any key must contain B and at least one of the other two attributes. Such a set therefore contains AB or BC. The only larger possibility ABC is a superkey but not a minimal key, because either of those proper subsets already determines R. Hence the complete candidate-key set is {AB,BC}, not just the first key suggested by the dependency AB→C. No extra dependencies are assumed.

# GATE 1995: Q89 (printed B Q27(a))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204046/GATE1995.pdf#page=8), physical page 8. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, Unallocated leaf; group total 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** π_PNAME(PUBLISHER).

**Essential problem context (paraphrased):** AUTHOR(ANAME,INSTITUTION,ACITY,AGE), PUBLISHER(PNAME,PCITY), BOOK(TITLE,ANAME,PNAME). Use relational algebra SELECT, PROJECT, JOIN and/or DIVIDE. Obtain the names of all publishers.

## Solution

The requested output is a single attribute, PNAME, from every tuple of PUBLISHER. Projection selects columns, so the expression is π_PNAME(PUBLISHER). No selection predicate is needed because no publisher is to be filtered out, and no join is needed because the required data already reside in one relation.

Under classical relational algebra, relations are sets, so projection returns each distinct publisher name once. If two stored tuples happen to share a name, the output still contains that value once. The result schema consists only of PNAME, not PCITY.

It would be incorrect to obtain these names by projecting BOOK: that would return only publishers represented by at least one recorded book, whereas the query asks for all publishers. Similarly, joining PUBLISHER with BOOK first could incorrectly lose a publisher with no matching book. DIVIDE is also unnecessary: there is no requirement involving all members of another relation. This simple query tests matching the requested output columns and population directly to the base relation.

# GATE 1995: Q90 (printed B Q27(b))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204046/GATE1995.pdf#page=8), physical page 8. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, Unallocated leaf; group total 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** π_ANAME,INSTITUTION,ACITY,AGE(AUTHOR ⋈ σ_PNAME='TECHNICAL PUBLISHERS'(BOOK)).

**Essential problem context (paraphrased):** AUTHOR(ANAME,INSTITUTION,ACITY,AGE), PUBLISHER(PNAME,PCITY), BOOK(TITLE,ANAME,PNAME). Use relational algebra SELECT, PROJECT, JOIN and/or DIVIDE. Obtain all AUTHOR attributes of authors who have published a book with PNAME='TECHNICAL PUBLISHERS'.

## Solution

First identify the relevant books using selection: T=σ_PNAME='TECHNICAL PUBLISHERS'(BOOK). This keeps tuples whose publisher name matches the specified literal, while retaining TITLE and ANAME so that authors can be linked. Next compute AUTHOR⋈T. The only shared attribute name is ANAME, so this natural join matches each qualifying book to its author record. Finally project ANAME,INSTITUTION,ACITY,AGE to return exactly the attributes requested from AUTHOR.

Thus the complete expression is π_ANAME,INSTITUTION,ACITY,AGE(AUTHOR⋈σ_PNAME='TECHNICAL PUBLISHERS'(BOOK)). Equivalently, first project ANAME from the selected books, then join that name relation to AUTHOR; the result already has exactly the AUTHOR schema.

An author with several matching books still appears only once in classical set relational algebra after projection. An author with no such book is excluded because there is no matching join tuple. Joining PUBLISHER is not needed: the condition is already expressible using BOOK.PNAME. The expression uses the association specified by the schema, namely ANAME as the author link; it does not infer that names uniquely identify people outside this database model. DIVIDE would express a universal requirement and would be inappropriate for the existential condition 'has published a book'.

# GATE 1995: Q91 (printed B Q27(c))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204046/GATE1995.pdf#page=8), physical page 8. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, Unallocated leaf; group total 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** π_ANAME(AUTHOR ⋈ BOOK ⋈ σ_PCITY='Madras'(PUBLISHER)).

**Essential problem context (paraphrased):** AUTHOR(ANAME,INSTITUTION,ACITY,AGE), PUBLISHER(PNAME,PCITY), BOOK(TITLE,ANAME,PNAME). Use relational algebra SELECT, PROJECT, JOIN and/or DIVIDE. Obtain the names of all authors who have published a book for any publisher located in Madras.

## Solution

Select publishers by their city: M=σ_PCITY='Madras'(PUBLISHER). Join BOOK to M on the common attribute PNAME. This keeps exactly books whose publisher is among the Madras publishers. Join the result to AUTHOR on ANAME, and finally project ANAME. A full expression is π_ANAME(AUTHOR⋈BOOK⋈σ_PCITY='Madras'(PUBLISHER)). Natural joins are unambiguous here: BOOK and PUBLISHER share PNAME, while AUTHOR and BOOK share ANAME. ACITY and PCITY are different attributes.

The test is on the publisher's city PCITY, not the author's city ACITY. An author outside Madras qualifies if at least one book has a Madras publisher. Conversely an author living in Madras does not qualify solely because of that residence. The word 'any' here is existential: one matching publisher is enough, so use selection and join rather than division.

Under an assumed foreign-key constraint BOOK.ANAME references AUTHOR.ANAME, the AUTHOR join can be omitted and π_ANAME(BOOK⋈M) is equivalent. Since that referential constraint is not explicitly stated, retaining AUTHOR is the safer literal expression for names of stored authors. Projection removes repetitions caused by multiple qualifying books or publishers under set semantics. Exact comparison uses the displayed city value 'Madras', not a silently substituted modern place-name string.
