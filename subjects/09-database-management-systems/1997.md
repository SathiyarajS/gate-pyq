

# GATE 1997: Q49 (printed A Q6.9)

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203902/GATE1997.pdf#page=6), physical page 6. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** MCQ, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** A: 1NF but not 2NF

**Essential problem context (paraphrased):** R(a, b, c, d) has atomic domains and only FDs a→c, b→d and their consequences. Which normal form applies?

## Solution

Neither a nor b can be derived from the other attributes, so every key must contain both. The closure of ab includes c and d, so ab is the candidate key. Attribute c depends on only a, and d on only b, both proper subsets of that composite key. These are partial dependencies of nonprime attributes, violating 2NF. Atomic domains establish 1NF, so A is correct. The statement that no other independent FDs hold rules out an unstated single-attribute key that would alter this analysis.

**Official answer:** Not available; no official key located.

**Independently derived answer:** D: insert S and delete R

**Essential problem context (paraphrased):** S.d references the primary key of R. Which can violate this reference: insert R, insert S, delete R, delete S?

## Solution

Inserting into S can introduce a nonnull d value absent from R. Deleting a referenced row from R can leave existing S rows without a parent. These are operations 2 and 3, D. Inserting a valid new R row cannot remove an existing reference target; deleting an S row removes a referencing requirement. This concerns the foreign-key constraint specifically, not a separate duplicate-primary-key violation on insertion into R. A DBMS may reject or cascade dangerous operations, but those enforcement policies do not change which raw changes can create a violation.

# GATE 1997: Q78 (printed B Q19(a))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203902/GATE1997.pdf#page=9), physical page 9. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** ℓ−1 internal key entries.

**Essential problem context (paraphrased):** In this question a B+-tree of order d has d to 2d key entries in each nonroot internal node, and an internal node with M keys has M+1 children. An internal root has 1 to 2d keys. All leaves are at equal edge-distance h from the root. Use this stated convention, not the alternative convention that “order” means maximum fan-out. With ℓ≥2 leaves, how many key entries are stored across all internal nodes?

## Solution

Let I be the number of internal nodes and let k_v be the number of key entries in internal node v. That node has k_v+1 children, so summing all internal-node child counts counts every tree edge exactly once:

Σ_internal v (k_v+1) = number of edges.

The whole tree has I+ℓ nodes and is connected and acyclic, so it has I+ℓ−1 edges. Therefore

Σ k_v + I = I+ℓ−1,
and hence Σ k_v = ℓ−1.

This argument includes the root, whose minimum occupancy differs from other internal nodes. It does not depend on the height, branching distribution, or order d, only on the fact that every internal node has one more child than key entries.

For a root with three leaf children, there are two root keys and ℓ−1=2. If an internal node with five leaf children is inserted one level lower, its four keys and the necessary separator keys above it still obey the same identity. The result counts stored separator entries in internal nodes; it is not the number of data records in the leaves, nor a claim about the number of distinct values across the entire B+-tree. Leaf keys can have different occupancy conventions without affecting this edge-count identity.

# GATE 1997: Q79 (printed B Q19(b))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203902/GATE1997.pdf#page=9), physical page 9. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 1 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** 13 internal nodes, attainable at height 3.

**Essential problem context (paraphrased):** In this question a B+-tree of order d has d to 2d key entries in each nonroot internal node, and an internal node with M keys has M+1 children. An internal root has 1 to 2d keys. All leaves are at equal edge-distance h from the root. Use this stated convention, not the alternative convention that “order” means maximum fan-out. For d=4 and exactly 52 leaves, find the maximum number of internal nodes.

## Solution

With 52 leaves, the total number of internal key entries is 52−1=51. If there are I internal nodes, the root uses at least one key and every other internal node uses at least d=4. Hence

1+4(I−1)≤51,
so 4I≤54 and I≤13.

An upper bound alone is not enough: equal leaf depth might prevent attaining it. Here it is attainable. Build a height-3 tree as follows:
Depth 0: one root with two children (one key).
Depth 1: two internal nodes, each with five children (four keys each).
Depth 2: ten internal nodes. Give eight of them five leaf children and two of them six leaf children.
Depth 3: 8·5+2·6=52 leaves.

Every nonroot internal node has five or six children, within the permitted five-to-nine range for d=4. All leaves are at depth three. The internal-node count is 1+2+10=13, and their key total is 1+8+8·4+2·5=51, confirming the arithmetic.

Thus 13 is both an upper bound and an achievable maximum. Treating order 4 as a maximum of four children would use a different B+-tree definition and give a wrong result for the convention explicitly supplied in this paper.

# GATE 1997: Q80 (printed B Q19(c))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203902/GATE1997.pdf#page=9), physical page 9. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** 2(d+1)^(h−1).

**Essential problem context (paraphrased):** In this question a B+-tree of order d has d to 2d key entries in each nonroot internal node, and an internal node with M keys has M+1 children. An internal root has 1 to 2d keys. All leaves are at equal edge-distance h from the root. Use this stated convention, not the alternative convention that “order” means maximum fan-out. For h≥1, find the minimum number of leaves.

## Solution

Since h≥1, the root is internal. Its minimum one key gives a minimum of two children. Every other internal node has at least d keys, hence at least d+1 children.

At depth 1 there are therefore at least 2 nodes. At depth 2 there are at least 2(d+1), and continuing to the leaf level h gives

minimum leaves = 2(d+1)^(h−1).

The exponent is h−1 because the first branching step is performed by the root, with minimum fan-out two; the remaining h−1 steps have minimum fan-out d+1. Multiplying by d rather than d+1 would confuse the minimum number of keys with the number of child pointers.

The bound is attainable: give the root exactly two children and every other internal node exactly d+1 children, stopping with leaves at depth h. All nonroot internal nodes then have exactly d keys, the root has exactly one, and every leaf lies at the required common depth. For h=1 the tree is a root with two leaf children, and the formula gives 2. For d=4,h=3 it gives 2·5²=50 leaves, consistent with the 52-leaf construction in the companion part. A tree of height zero is outside this subpart and would instead consist of a single leaf.

# GATE 1997: Q99 (printed B QGFG76(a))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203902/GATE1997.pdf#page=12), physical page 12. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 1 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** After qualifying SELECT EMP.eno, the set-algebra answer is π_EMP.eno(σ_EMP.eno=INVOLVED.eno ∧ INVOLVED.pno=3(EMP×INVOLVED)). Literal SQL has an ambiguous column reference.

**Essential problem context (paraphrased):** Relations are EMP(eno,name,age), PROJ(pno,name), and INVOLVED(eno,pno). EMP.eno and PROJ.pno are shown as primary keys; no primary key is visibly underlined for INVOLVED. EMP describes employees, PROJ projects, and INVOLVED employee–project participation. Use ordinary set relational algebra unless a different model is explicitly stated. Translate the supplied SQL using relational-algebra operators:
SELECT eno
FROM EMP, INVOLVED
WHERE EMP.eno = INVOLVED.eno AND INVOLVED.pno = 3;
The SELECT column is unqualified in the reproduction.

## Solution

First distinguish the printed query from its evident intention. Both EMP and INVOLVED have a column named eno, and an explicit FROM EMP,INVOLVED cross join retains both column names. The equality in WHERE does not make the unqualified SELECT eno syntactically unambiguous in standard SQL. The literal query therefore requires qualification. Taking the intended target as EMP.eno gives:

π_EMP.eno(σ_EMP.eno=INVOLVED.eno ∧ INVOLVED.pno=3(EMP × INVOLVED)).

The Cartesian product produces all employee/participation row pairs. Selection keeps only pairs referring to the same employee and project number 3. Projection then retains the requested employee number. One may push the project filter down before the product, obtaining π_EMP.eno(σ_EMP.eno=INVOLVED.eno(EMP × σ_pno=3(INVOLVED))), which is set-equivalent and usually more efficient.

Attribute qualification in the first formula prevents confusion between the two eno fields and the two relations. A natural join EMP ⋈ INVOLVED followed by σ_pno=3 and π_eno is also valid here because eno is their only shared attribute name. PROJ is not used: the SQL never checks whether project 3 exists in PROJ, and adding that join would impose an extra condition not present in the query.

There is also a set-versus-bag caveat. Ordinary relational algebra removes duplicates in projection, whereas SELECT without DISTINCT uses SQL bag semantics. If duplicate INVOLVED rows are allowed, the SQL can return repeated employee numbers. For example, two copies of involvement (7,3) yield two SQL rows for employee 7 but one set-algebra tuple. No visible INVOLVED key guarantees their absence. Thus the displayed algebra represents the intended distinct set of employee numbers. Exact bag equivalence requires bag algebra, SELECT DISTINCT, or a uniqueness assumption; this distinction should not be hidden behind the column-name repair.

**Independently derived answer:** Employee numbers of involved employees who participate in every project.

**Essential problem context (paraphrased):** Relations are EMP(eno,name,age), PROJ(pno,name), and INVOLVED(eno,pno). EMP.eno and PROJ.pno are shown as primary keys; no primary key is visibly underlined for INVOLVED. EMP describes employees, PROJ projects, and INVOLVED employee–project participation. Use ordinary set relational algebra unless a different model is explicitly stated. In at most 15 words state what this relational-algebra expression determines:
π_eno(INVOLVED) − π_eno((π_eno(INVOLVED) × π_pno(PROJ)) − INVOLVED).
The two b-subparts together carry 4 marks; their individual marks are not printed.

## Solution

Requested short answer: Employee numbers of involved employees who participate in every project.

This is 10 words, within the requested limit. The wording involved employees preserves the candidate domain actually used by the expression. For the derivation, let C=π_eno(INVOLVED) be the employee numbers appearing in at least one involvement row, let P=π_pno(PROJ) be all project numbers, and let R=INVOLVED.

The product C×P enumerates every employee–project pair that would be required if each candidate participated in every project. Subtracting R leaves missing pairs: a pair (e,p) remains exactly when e is a candidate, p is a project, and the participation (e,p) is absent. Projecting those missing pairs onto eno produces the candidates who fail to participate in at least one project. Finally, subtracting that set from C leaves the candidates with no missing project.

Formally, the result is {e∈C: for every p∈P, (e,p)∈R}. This is the usual division construction R÷P with its candidate universe drawn from R. For example, if P={1,2}, candidate 7 appears with both projects and candidate 8 only with project 1, the missing-pair set contains (8,2), so only 7 remains.

Two boundary details matter. EMP is not referenced, so the expression does not independently check that every eno is a valid employee if referential integrity is absent. If PROJ is empty, C×P is empty, the missing-candidate set is empty, and the result is C by vacuous truth. It is not automatically all rows of EMP; employees absent from INVOLVED are outside the candidate universe even in that empty-project case. The short answer is therefore narrower and more faithful than an unconditional claim that all employees participating in every project are returned.

The second operator is printed as a projection symbol whose subscript is a comparison, rather than a projection of an attribute followed by a selection. ## Solution

Literal reading first: in standard relational algebra, π takes an attribute list, not a Boolean comparison predicate. The printed subscript E.age<EMP.age therefore does not define an ordinary projection. Simply changing that π into σ is insufficient: it would produce tuples of the two-relation product, which cannot be subtracted from the unary relation π_age(EMP). Set difference requires compatible schemas. Consequently the supplied reproduction, as read, does not have a defined standard relational-algebra result. No verified original or alternate complete tail is available to establish the missing symbols.

A plausible intended repair is
π_age(EMP) − ρ_age←E.age(π_E.age(σ_E.age<EMP.age(ρ_E(EMP) × EMP))).
Here ρ_E(EMP) is a distinct copy whose attributes are qualified E. The inner selection finds each pair where the copied employee is younger than the other employee. Projecting E.age collects ages that have a strictly greater age somewhere in EMP. The explicit attribute rename makes the right-hand unary age relation union-compatible with the left-hand one. Subtract those nonmaximum ages from all ages and only the maximum age remains.

Under this repair, the requested short English answer is: Ages of the oldest employees. This is five words. For ages {25,40,40}, the Cartesian comparison finds that 25 has an older witness, while 40 does not. Set projection removes duplicate 40s, and the final result is {40}, an age value rather than employee names or employee records. With an empty EMP, the result is empty. Equal ages do not eliminate each other because the comparison is strict.

This maximum-age interpretation is conditional on projecting the younger copy's age. Projecting EMP.age instead would remove ages that have a smaller witness and leave the minimum, a different query. Thus the damaged expression cannot safely be repaired silently. The literal defect and the proposed older-witness interpretation must remain separate until a better source establishes the exact original notation.
