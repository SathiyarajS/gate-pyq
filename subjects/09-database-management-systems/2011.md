**Paraphrased problem context:** A student table has one row per registered student: Registration_Num is unique per student; UID is nationally unique per citizen; BankAccount_Num stores a primary account, and students may have multiple or joint accounts; Name is the student's name; Hostel_Room is the room number. Which statement is INCORRECT?

(A) BankAccount_Num is a candidate key
(B) Registration_Num can be a primary key
(C) UID is a candidate key if all students are from the same country
(D) If S is a superkey and S intersect UID is NULL, S union UID is also a superkey

## Solution

Joint accounts allow two students to have the same primary BankAccount_Num, so it need not uniquely identify a student and is not guaranteed to be a candidate key. Registration numbers are unique; a national UID is unique under the stated same-country assumption; adding an attribute to a superkey preserves uniqueness. Therefore A is incorrect. NULL in the set expression is understood as empty intersection, not SQL NULL.

A candidate key must uniquely identify rows and be minimal for that purpose. A unique account number uniquely identifies a bank account, but the table stores students: joint holders can legitimately repeat the account number across student rows. Conversely, unique registration numbers identify students directly. In D, the extra UID attribute cannot create a collision between rows already distinguished by S; minimality may be lost, but superkey status is preserved.

**Source access:** Archived official IIT Kharagpur paper and IIT Madras key, booklet A. Physical PDF page numbers are used; code A is the matching key column. Final-revision designation is unverified.

**Paraphrased problem context:** Table T has integer columns X,Y and starts with (1,1). Let MX and MY be their current respective maxima. Perform 128 additional inserts of (MX+1,2*MY+1), recomputing maxima after each insert. What does SELECT Y FROM T WHERE X=7 return?

(A) 127
(B) 255
(C) 129
(D) 257

## Solution

The rows obey X=k and Y=2^k−1 by induction from(1, 1): the next maximum Y is doubled and increased by 1. Hence the row X=7 has Y=127, A. Completing all 128 additional inserts would require representing 2^129−1 in the final row, beyond common fixed-width SQL INTEGER types. The problem’s statement that all inserts occur therefore assumes sufficiently large integers or an abstract unbounded-integer model; the requested early row itself is representable.

The early rows make the indexing clear: (1,1),(2,3),(3,7),(4,15),(5,31),(6,63),(7,127). Since X increases strictly, there is exactly one row with X=7. For a formal recurrence, set Z=Y+1; then Z doubles at each step, with Z=2 initially, so at X=k it equals 2^k. The query is not asking for the final maximum after all 128 inserts; that confusion produces inappropriate much larger powers.

**Paraphrased problem context:** A sufficiently large relation r has attributes A1,...,An, with 1≤p≤n. Q1 projects A1,...,Ap after selection Ap=c. Q2 projects the same attributes after selection c1≤Ap≤c2. The database may use ordered indexing or hashing on Ap. Which statement is intended to be TRUE?

(A) Ordered indexing always outperforms hashing for both
(B) Hashing always outperforms ordered indexing for both
(C) Hashing outperforms ordered indexing on Q1, but not Q2
(D) Hashing outperforms ordered indexing on Q2, but not Q1

## Solution

Q1 is equality on the indexed attribute, where a well-distributed hash index normally locates its bucket in expected constant time and outperforms ordered search. Q2 is a range predicate, for which an ordered index finds the first qualifying entry and scans the interval; hashing lacks that order. Thus C is the conventional comparison. Actual performance also depends on collisions, selectivity, caching and index layout, so this is not a universal measured-time guarantee for every database.

Hashing sends equal keys to a bucket but does not put nearby numerical values in nearby buckets. Thus an equality predicate can use one hash lookup plus collision handling, whereas a range may require examining many buckets. A sorted index can locate the lower bound and walk adjacent entries until the upper bound. Projection of columns A1,...,Ap does not change this key distinction between the selection predicates. The source's absolute performance wording is stronger than what can be guaranteed without a storage cost model.

**Paraphrased problem context:** Loan_Records has columns Borrower,Bank_Manager,Loan_Amount and rows (Ramesh,Sunderajan,10000.00), (Suresh,Ramgopal,5000.00), (Mahesh,Sunderajan,7000.00). Evaluate SELECT count(*) FROM ((SELECT Borrower,Bank_Manager FROM Loan_Records) AS S NATURAL JOIN (SELECT Bank_Manager,Loan_Amount FROM Loan_Records) AS T).

(A) 3
(B) 9
(C) 5
(D) 6

## Solution

The common column of the two projections is Bank_Manager. Sunderajan appears in two rows of each projection, so the natural join yields 2×2=4 combinations for that manager. Ramgopal appears once in each projection, yielding 1×1=1 combination. COUNT(*) returns 4+1=5, option C. The join does not pair rows by their original borrower, since Borrower is absent from the second projection.

The projected left rows are (Ramesh,Sunderajan),(Suresh,Ramgopal),(Mahesh,Sunderajan). The right rows are (Sunderajan,10000),(Ramgopal,5000),(Sunderajan,7000). Each of Ramesh and Mahesh joins with both Sunderajan amounts, yielding four rows; Suresh joins with the single Ramgopal amount. COUNT(*) counts those joined rows, including combinations that were not in the original table. Joining projections can create extra combinations whenever their common attribute is not a key.
