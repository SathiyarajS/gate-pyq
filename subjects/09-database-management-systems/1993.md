

# GATE 1993: Q50 (printed II-B Q14)

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204139/GATE1993.pdf#page=11), physical page 11. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** 2048 data blocks; 67 index blocks (64+2+1); 3 index levels, or 4 levels including data.

**Essential problem context (paraphrased):** An ISAM file has 16K records of 64 bytes including a 14-byte key. A block address needs 2 bytes; disk blocks are 512 bytes. Find data blocks, index blocks, and number of index-tree levels.

## Solution

Use K=1024, full blocks, unspanned fixed-length records, and the usual sparse ISAM index with one key-and-block-address entry per child block. Each data block holds floor(512/64)=8 records. Thus 16*1024/8=2048 data blocks are needed. The 14-byte key is already included in each 64-byte record; it must not be added again.

An index entry occupies 14+2=16 bytes, so an index block contains floor(512/16)=32 entries and can identify 32 child blocks. The lowest index level needs one entry for each of 2048 data blocks, giving ceil(2048/32)=64 index blocks. The next level indexes those 64 blocks and uses ceil(64/32)=2 blocks. A root indexes these two and fits in ceil(2/32)=1 block. Hence the total index area contains 64+2+1=67 blocks.

The hierarchy is:
root index: 1 block (2 populated entries)
    -> middle index: 2 blocks (64 entries in total)
        -> bottom index: 64 blocks (2048 entries in total)
            -> data: 2048 blocks (16384 records).

There are three index levels, excluding the data level. If all levels including data are counted, the root-to-record path spans four levels; that is a different counting convention. The data area occupies 2048*512=1,048,576 bytes, and the allocated index area occupies 67*512=34,304 bytes, including root slack. There are 2115 blocks overall. No overflow reserve, block header overhead, or occupancy factor is supplied, so none is invented. A dense record-level index would have a different size and is not the standard sparse ISAM interpretation used here.

# GATE 1993: Q61 (printed II-C Q23)

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204139/GATE1993.pdf#page=14), physical page 14. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** DESCRIPTIVE, 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Use EXISTS to correlate enrollment and teaching to each student.

**Essential problem context (paraphrased):** STUDENTS(rollno key,sname,saddr), COURSES(cno key,cname), ENROLL(rollno,cno composite key,grade), TEACH(tno,cno composite key,tname). FDs: rollno→sname,saddr; cno→cname; tno→tname; rollno,cno→grade. The reproduced cao/sdaddr spellings are interpreted as cno/saddr. Retrieve roll number and name of students with grade A in at least one course taught by a teacher named Ramesh.

## Solution

A student qualifies if some enrollment has their roll number and grade A, and some teaching row for that enrollment's course has tname='Ramesh'. The course number is the join between ENROLL and TEACH; names need not be unique teacher identifiers.

SELECT s.rollno, s.sname
FROM STUDENTS AS s
WHERE EXISTS (
  SELECT 1 FROM ENROLL AS e
  JOIN TEACH AS t ON t.cno=e.cno
  WHERE e.rollno=s.rollno
    AND e.grade='A' AND t.tname='Ramesh'
);

EXISTS yields one truth value for each outer student, so several qualifying courses or several teachers named Ramesh do not duplicate the output. A plain join version would need DISTINCT for that purpose. The COURSES relation is unnecessary because the query does not request a course name or another condition on it. No requirement says the student must have an A in every Ramesh-taught course; replacing EXISTS with universal division would answer a stronger question.

The source TEACH attribute is printed cao but described as course number cno, and its FD list prints sdaddr for saddr. These obvious naming inconsistencies are explicitly normalized in the query rather than treated as extra attributes.

# GATE 1993: Q62 (printed II-C Q24(a))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204139/GATE1993.pdf#page=14), physical page 14. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** DESCRIPTIVE, Unallocated leaf; group total 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** No: TEACH violates 3NF through tno→tname.

**Essential problem context (paraphrased):** STUDENTS(rollno key,sname,saddr), COURSES(cno key,cname), ENROLL(rollno,cno composite key,grade), TEACH(tno,cno composite key,tname). FDs: rollno→sname,saddr; cno→cname; tno→tname; rollno,cno→grade. The reproduced cao/sdaddr spellings are interpreted as cno/saddr. Is this database in 3NF?

## Solution

Treat each listed relation separately and use the supplied FDs as the schema constraints. In STUDENTS, rollno is a key and determines the other attributes; COURSES likewise has key cno. ENROLL's determinant (rollno,cno) is its key. These three relations therefore satisfy BCNF, and in particular 3NF, under the stated dependencies.

TEACH has declared composite key (tno,cno). The dependency tno→tname is nontrivial, but tno alone does not determine cno, so it is not a superkey. The dependent attribute tname is not a member of the candidate key and is nonprime. This violates the 3NF test that every nontrivial FD have a superkey determinant or prime right-side attribute. Indeed it is already a partial dependency of a nonprime attribute on part of the composite key, violating 2NF.

Do not infer that tno is a key simply because it identifies a teacher: a teacher can occur in several teaching rows, one per course. No additional FD tno→cno is supplied. If such a different constraint were imposed the answer could change, but it is not part of this schema.

# GATE 1993: Q63 (printed II-C Q24(b))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204139/GATE1993.pdf#page=14), physical page 14. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** DESCRIPTIVE, Unallocated leaf; group total 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Keep STUDENTS,COURSES,ENROLL; replace TEACH with TEACHER(tno key,tname) and TEACHES(tno,cno composite key).

**Essential problem context (paraphrased):** STUDENTS(rollno key,sname,saddr), COURSES(cno key,cname), ENROLL(rollno,cno composite key,grade), TEACH(tno,cno composite key,tname). FDs: rollno→sname,saddr; cno→cname; tno→tname; rollno,cno→grade. The reproduced cao/sdaddr spellings are interpreted as cno/saddr. Normalize the relations to 3NF if needed.

## Solution

Separate teacher facts from teaching assignments. Use TEACHER(tno,tname) with primary key tno, and TEACHES(tno,cno) with primary key (tno,cno). Retain the other three relations unchanged. The dependency tno→tname now has a key determinant in TEACHER; no supplied nontrivial non-key dependency remains in TEACHES. Thus both components are BCNF, stronger than the requested 3NF.

This decomposition is lossless under the given FD. Its intersection is {tno}, which determines all of TEACHER. More concretely, every teaching pair joins to its unique teacher name, and rows sharing a teacher number cannot acquire different names because of the FD. Projecting a valid original TEACH relation and joining the projections therefore reconstructs it without spurious combinations of teacher names and assignments.

It also preserves the relevant dependency locally in TEACHER. Separating tname into a relation with only cno instead would attach a teacher name to a course rather than its determining teacher number, and would not preserve the intended dependency. Identical names across different teacher numbers remain permitted.
