

# GATE 2009: Q43 (printed CS Q43)

**Question:** [Official-source archive](https://drive.google.com/file/d/1popAHO-cX69oQEx_tD0wZXL1tTrBljeO/view), member CS/CS2009.pdf, physical page 10. Consult original wording and choices.

**Type / marks:** MCQ, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** B

**Paraphrased problem context:** T1=R1x, W1x, W1y; T2=R2x, R2y, W2y. S1=R1x, R2x, R2y, W1x, W1y, W2y; S2=R1x, R2x, R2y, W1x, W2y, W1y; S3=R1x, W1x, R2x, W1y, R2y, W2y; S4=R2x, R2y, R1x, W1x, W1y, W2y. Which are conflict-serializable? A S1/S2; B S2/S3; C S3 only; D S4 only.

## Solution

S1 has T2→T1 from r2(x) before w1(x), but T1→T2 from w1(y) before w2(y), so it cycles. S2 has only T2→T1: both its reads and final write of y precede T1’s conflicting writes. S3 has only T1→T2, as w1(x) and w1(y) precede T2’s accesses. S4 cycles for the same opposing x and y directions as S1. Therefore S2 and S3 are conflict-serializable, B.

Teaching detail:
Build one vertex per transaction and add an edge when an earlier operation conflicts with a later operation of the other transaction on the same item, with at least one write. Reads of different items or two reads do not conflict. S2 has only 2→1, so it is equivalent to serial T2, T1; S3 has only 1→2. S1/S4 each contain both directions and therefore a directed cycle. Acyclicity, not whether operations are interleaved, determines conflict serializability.

# GATE 2009: Q45 (printed CS Q45)

**Question:** [Official-source archive](https://drive.google.com/file/d/1popAHO-cX69oQEx_tD0wZXL1tTrBljeO/view), member CS/CS2009.pdf, physical page 10. Consult original wording and choices.

**Type / marks:** MCQ, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** A

**Paraphrased problem context:** Relations r on R={a, b, c}, s on S={c}. I=π_ab(r)−π_ab((π_ab(r)×s)−r). II={t∈π_ab(r):∀u∈s ∃v∈r(u=v[c]∧t=v[ab])}. III replaces that quantification by∀v∈r ∃u∈s with the same equality predicates. IV SELECT R.a, R.b FROM R, S WHERE R.c=S.c. Which pair is equivalent? A I/II; B I/III; C II/IV; D III/IV.

## Solution

I begins with candidate(a, b) pairs from r and removes those for which some c in s is missing from r, exactly relational division r÷s. II expresses the same condition: for every tuple u in s there exists a tuple v in r matching both u’s c and the candidate(a, b). Thus I and II are equivalent, A, including empty s because both restrict candidates to the projection of r. III reverses the quantifiers and requires all r tuples to share the candidate pair; IV is only an existential matching join, not universal division.

Teaching detail:
Division asks for candidates paired with every c in s. Expression I constructs all required candidate/c combinations, subtracts actual tuples to find missing combinations, then removes the candidates with any missing one. II directly quantifies the same every-c requirement. A join only requires at least one matching c, so IV cannot replace division. Empty s is handled consistently because both I and II retain candidates only fromπ_ab(r), rather than introducing an infinite domain.

# GATE 2009: Q55 (printed CS Q55)

**Question:** [Official-source archive](https://drive.google.com/file/d/1popAHO-cX69oQEx_tD0wZXL1tTrBljeO/view), member CS/CS2009.pdf, physical page 13. Consult original wording and choices.

**Type / marks:** MCQ, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** D

**Paraphrased problem context:** Schema Suppliers(sid key, sname, city, street), Parts(pid key, pname, color), Catalog(sid, pid composite key, cost). Query SELECT S.sname FROM Suppliers S WHERE S.sid NOT IN(SELECT C.sid FROM Catalog C WHERE C.pid NOT IN(SELECT P.pid FROM Parts P WHERE P.color<>blue)). Relations nonempty. Options suppliers who A supplied a non-blue part; B have not supplied a non-blue part; C supplied only blue parts; D have not supplied only blue parts. Preserve SQL-null/referential-integrity and wording qualifications.

## Solution

The innermost query finds non-blue part IDs. The middle query finds supplier IDs for catalog rows whose part is not in that set, i.e. suppliers of a blue part under the intended referential-integrity and non-NULL color assumptions. The outer NOT IN therefore returns names of suppliers who supply no blue parts, including suppliers with no catalog rows. The intended option is D, but its printed wording is imprecise: “have not supplied only blue parts” logically also includes mixed-color suppliers, whereas the SQL excludes them. A asks for any non-blue supply and also includes mixed suppliers; B and C concern suppliers with no non-blue supply / only blue supply, the opposite condition. Thus no option states the exact result under a literal reading. Do not present D as an officially verified or exact semantic equivalence.

Teaching detail:
Read the nested NOT IN clauses from inside out. First collect non-blue part IDs; next collect suppliers with a catalog part outside that set, meaning a blue part under non-null referential-integrity assumptions; finally exclude those suppliers. The result is suppliers with no blue supply, including suppliers with no catalog row. A supplier of both blue and red is excluded. That mixed-supply example demonstrates why printed D is not literally equivalent to the SQL despite being the intended choice. The discrepancy is semantic, not a reason to invent an official key.

# GATE 2009: Q56 (printed CS Q56)

**Question:** [Official-source archive](https://drive.google.com/file/d/1popAHO-cX69oQEx_tD0wZXL1tTrBljeO/view), member CS/CS2009.pdf, physical page 13. Consult original wording and choices.

**Type / marks:** MCQ, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** A

**Paraphrased problem context:** For the preceding schema, supplier names and street names are unique within a city, and(sname, city) is a candidate key. No FDs other than those implied by primary/candidate keys are assumed. Choose A BCNF; B 3NF not BCNF; C 2NF not 3NF; D not 2NF.

## Solution

The given primary keys are Suppliers.sid, Parts.pid, and Catalog.(sid, pid); Suppliers additionally has candidate key (sname, city). The question explicitly rules out functional dependencies other than those implied by primary and candidate keys. Consequently every nontrivial FD has a superkey as determinant, exactly the BCNF condition. All three relations are in BCNF, option A. Do not infer street→city from an address or infer sname alone is a key: the stipulated uniqueness is within a city and (sname, city) is explicitly the candidate key.

Teaching detail:
BCNF tests every nontrivial FD X→Y and requires X to be a superkey. The source explicitly permits only dependencies implied by the listed keys, so all such determinants qualify. Do not invent dependencies from the meaning of street or supplier name beyond the stated within-city uniqueness. Thus the schema meets BCNF and consequently the weaker normal forms as well; A is the strongest correct listed description.
