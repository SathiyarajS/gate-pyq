**Independently derived answer:** B: mn and 0

**Essential problem context (paraphrased):** Relations R,S have m,n tuples. What are the maximum and minimum possible sizes of their join?

## Solution

A join selects qualifying pairs from R×S, which contains mn pairs. Therefore it cannot exceed mn. This upper bound occurs when every pair satisfies the join predicate. The minimum zero occurs when no pair satisfies it. Hence B gives the general possible extremes. This reasoning assumes an ordinary inner join with a condition that can permit or reject pairs. A fixed natural join on disjoint schemas is always the Cartesian product, so its minimum would not be zero for positive m,n; the question is the usual unrestricted join-bound comparison.

**Essential problem context (paraphrased):** Translate {t | t∈r and t[A]=10 and t[B]=20}. Options combine the two selections by OR/union, intersection, or difference.

## Solution

The tuple must satisfy both tests simultaneously. Selection on A=10 retains the first qualifying subset, and selection on B=20 retains the second. Their intersection contains exactly tuples passing both, so σ(A=10)(r)∩σ(B=20)(r) is equivalent, C. Union or a disjunctive predicate would admit a tuple satisfying only one test. Difference would keep the first test while rejecting the second, which reverses the required conjunction.

**Independently derived answer:** B

**Essential problem context (paraphrased):** Which comparison is correct: disk versus RAM exclusivity, faster B+-tree range queries, primary versus secondary exclusivity, or height independent of record count?

## Solution

B+-trees store the data entries at the leaf level and typically link those leaves in key order. After locating a range’s first entry, scanning successive leaves retrieves the remainder efficiently without repeated searches through internal nodes. This is the conventional range-query advantage in B. Both structures may be disk resident and can support different index roles, so A and C are false dichotomies. Height still increases with record count at a fixed fanout, making D false. The comparison assumes the standard linked-leaf B+-tree layout.

**Essential problem context (paraphrased):** Schedule: r1(A),r2(B),w1(A),r2(A),w2(A),w2(B),r1(B),w1(B). Is it serializable and/or possible under two-phase locking?

## Solution

The A conflicts put transaction 1 before transaction 2: w1(A) precedes r2(A) and w2(A). The B conflicts put transaction 2 before transaction 1: w2(B) precedes r1(B) and w1(B). Hence the precedence graph has a directed cycle. It is not conflict serializable; even view equivalence fails because T2 reads A from T1 while T1 reads B from T2, requiring opposite serial orders. Two-phase locking guarantees conflict serializability, so it cannot produce this completed schedule. Thus D.

**Essential problem context (paraphrased):** R(S,T,U,V) has S→T,T→U,U→V,V→S and is decomposed into R1,R2. Determine whether the components satisfy 2NF and 3NF.

## Solution

By following the dependency cycle, each single attribute determines all four. Consequently, in any projected component, every individual attribute determines all attributes of that component and is a key. Every nontrivial projected FD therefore has a superkey determinant, so each component is in BCNF, hence also 3NF and 2NF. Thus D. This normal-form argument does not depend on whether the components intersect. The reproductions differ on that intersection symbol; normal form alone does not establish lossless decomposition.

# GATE 1999: Q87 (printed B Q22(a))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203805/GATE1999.pdf#page=9), physical page 9. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Join EMP to DEPT and filter Location=Calcutta and Salary>50000.

**Essential problem context (paraphrased):** EMP(Employee-no, Dept-no, Employee-name, Salary), DEPT(Dept-no, Dept-name, Location). Return employee names whose department is located at Calcutta and salary exceeds Rs.50,000.

## Solution

Use the common department identifier to join each employee to their department, then apply both predicates:

SELECT e."Employee-name"
FROM EMP AS e
JOIN DEPT AS d ON d."Dept-no" = e."Dept-no"
WHERE d.Location = 'Calcutta'
  AND e.Salary > 50000;

The double quotes are standard SQL identifier quoting, required here because the printed attribute names contain hyphens. A database schema using Employee_name and Dept_no may use those unquoted names instead. The inequality is strict: salary exactly 50000 does not qualify. The department join is essential because Location belongs to DEPT, not EMP. This returns one row per matching employee under the usual department-key assumption; two employees sharing a name may produce duplicate name values. Add DISTINCT only if the intended output is a set of distinct names rather than names per employee. SQL NULL salaries do not pass the comparison.

# GATE 1999: Q88 (printed B Q22(b))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203805/GATE1999.pdf#page=9), physical page 9. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 3 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** LEFT JOIN all departments to qualifying employees and count the matching employee department values, including zeros.

**Essential problem context (paraphrased):** EMP(Employee-no, Dept-no, Employee-name, Salary), DEPT(Dept-no, Dept-name, Location). For each department number, count employees whose salary exceeds Rs.1,00,000.

## Solution

To interpret “for each department” literally, start from DEPT so that departments with zero qualifying employees are retained:

SELECT d."Dept-no", COUNT(e."Dept-no") AS high_salary_count
FROM DEPT AS d
LEFT JOIN EMP AS e
  ON e."Dept-no" = d."Dept-no"
 AND e.Salary > 100000
GROUP BY d."Dept-no";

The salary condition belongs in ON: placing it in WHERE would discard the null-extended rows and remove zero-count departments. COUNT(e."Dept-no") counts only actual matches, since a matched equality implies a non-null employee department value; COUNT(*) would incorrectly count the null-extended row as one. Salaries equal to 100000 do not qualify. This assumes the conventional unique department number in DEPT.
If the expected interpretation asks only for department numbers represented by qualifying employees, the shorter traditional query is:
SELECT "Dept-no", COUNT(*) AS high_salary_count
FROM EMP
WHERE Salary > 100000
GROUP BY "Dept-no";
That version omits zero-count departments. It is a different coverage choice, so the all-department query is preferable for the literal wording. Attribute names are quoted to preserve the printed hyphens.
