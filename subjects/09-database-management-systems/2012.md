**Paraphrased problem context:** Which of the following is TRUE?
       (A) Every relation in 3NF is also in BCNF
       (B) A relation R is in 3NF if every non-prime attribute of R is fully functionally dependent on every
           key of R
       (C) Every relation in BCNF is also in 3NF
       (D) No relation can be in both BCNF and 3NF

## Solution

BCNF requires every determinant of a nontrivial functional dependency to be a superkey. This satisfies the 3NF alternative that the determinant is a superkey or the dependent attribute is prime. Therefore BCNF implies 3NF, C. The converse need not hold. Full dependence of non-prime attributes on keys describes the 2NF condition and does not by itself exclude transitive dependencies.

Worked check / additional reasoning: For a concrete 3NF-not-BCNF schema, take R(A,B,C) with AB→C and C→B. Candidate keys are AB and AC. C→B violates BCNF because C is not a superkey, but satisfies 3NF because B is prime.

**Paraphrased problem context:** Given the basic ER and relational models, which of the following is INCORRECT?
        (A) An attribute of an entity can have more than one value
        (B) An attribute of an entity can be composite
        (C) In a row of a relational table, an attribute can have more than one value
        (D) In a row of a relational table, an attribute can have exactly one value or a NULL value

## Solution

The basic ER model can represent composite and multivalued attributes. In the ordinary first-normal-form relational representation, however, each cell contains a single atomic value (or the SQL-style NULL marker admitted by the options), not several values for that attribute. Therefore C is the incorrect statement. Multivalued ER attributes need a separate relational representation.

Worked check / additional reasoning: An ER address can have components such as city and postcode, and an ER person can have several phone numbers. Mapping to relations separates components into columns and multiple phone values into rows of a related table rather than storing a set in one atomic cell.

**Paraphrased problem context:** Which of the following statements are TRUE about an SQL query?

        P : An SQL query can contain a HAVING clause even if it does not have a GROUP BY clause
        Q : An SQL query can contain a HAVING clause only if it has a GROUP BY clause
        R : All attributes used in the GROUP BY clause must appear in the SELECT clause
        S : Not all attributes used in the GROUP BY clause need to appear in the SELECT clause
        (A) P and R             (B) P and S              (C) Q and R             (D) Q and S

## Solution

P is true: SELECT COUNT(*) FROM T HAVING COUNT(*)>0 is a valid aggregate query without GROUP BY, treating the input as one group. S is true: SELECT COUNT(*) FROM T GROUP BY a groups by a without selecting a. Therefore Q and R are false, and the correct pair is P and S, option B. The appended official Code A key instead prints C (Q and R). Preserve official C for scoring provenance and derived B as a documented source/key discrepancy; do not silently change either.

Worked check / additional reasoning: On a table with values a=1,1,2, grouping by a while selecting only COUNT(*) returns counts 2 and 1 without exposing a. On the same nonempty table, HAVING COUNT(*)>0 without GROUP BY retains its one aggregate group. These concrete cases refute both universal claims Q and R.

**Paraphrased problem context:** Consider the following transactions with data items P and Q initialized to zero:
        T1 :read (P);
            read (Q);
            if P = 0 then Q := Q + 1 ;
            write (Q).
        T2 : read (Q);
            read (P);
            if Q = 0 then P := P + 1 ;
            write (P).
        Any non-serial interleaving of T1 and T2 for concurrent execution leads to
        (A) a serializable schedule
        (B) a schedule that is not conflict serializable
        (C) a conflict serializable schedule
        (D) a schedule for which a precedence graph cannot be drawn

## Solution

Conflicts arise on P between T1’s read and T2’s write, and on Q between T2’s read and T1’s write. If w1(Q) precedes r2(Q), then all of T1’s listed operations precede T2’s first operation, giving serial order T1, T2. Similarly, w2(P) before r1(P) forces serial order T2, T1. Therefore every genuinely nonserial interleaving has r1(P)<w2(P) and r2(Q)<w1(Q), giving both T1→T2 and T2→T1 in the precedence graph. The cycle proves it is not conflict serializable, B. The question’s qualification nonserial is necessary.

Worked check / additional reasoning: The initial values affect the arithmetic outcomes but not the conflict edges, which depend on read/write order. Each transaction’s first read is before its last write; interleaving forces both cross-read-before-write relations, producing a directed two-cycle.

**Paraphrased problem context:** Let r1 and r2 be instances of R1(A,B) and R2(C,D). B is a foreign key referencing C, and referential integrity holds. Which is always true? π denotes projection.
(A) π_B(r1)−π_C(r2)=∅ (B) π_C(r2)−π_B(r1)=∅ (C) π_B(r1)=π_C(r2) (D) π_B(r1)−π_C(r2)≠∅.

## Solution

In the classical relational model used by the relational-algebra expression, every B value in r1 must occur as a C value in r2. Thus π_B(r1) is a subset of π_C(r2), and π_B(r1)−π_C(r2)=∅, A. Referenced C values need not all occur in B, so equality and reverse containment are not guaranteed. This is the textbook non-null relational interpretation; SQL nullable foreign keys require separate treatment of NULL.

Worked check / additional reasoning: For a concrete permitted instance, r1 may reference only C=1 while r2 contains C=1 and C=2. Then the forward difference is empty but the reverse difference contains 2. Referenced rows may exist even when no row currently references them.

Relational union eliminates the two shared tuples (15, Shreya, 24) and (99, Rohit, 11), leaving five distinct tuples with Id values 12, 15, 25, 98, 99. This is a theta join, so each qualifying pair contributes its combined tuple.

**Paraphrased problem context:** Relations: A(Id,Name,Age)={(12,Arun,60),(15,Shreya,24),(99,Rohit,11)}; B(Id,Name,Age)={(15,Shreya,24),(25,Hari,40),(98,Rohit,20),(99,Rohit,11)}; C(Id,Phone,Area)={(10,2200,02),(99,2100,01)}.
How many tuples result from this SQL query?
SELECT A.Id FROM A WHERE A.Age > ALL (SELECT B.Age FROM B WHERE B.Name='Arun');
(A) 4 (B) 3 (C) 0 (D) 1.

## Solution

There is no B row with Name=Arun, so the inner query returns an empty relation. A comparison quantified by ALL over an empty set is true: there is no counterexample. Consequently all three rows of A satisfy the WHERE condition, returning Id values 12, 15, 99. The count is 3, B.

Worked check / additional reasoning: ALL means every returned value satisfies the comparison, not that at least one value exists. NOT EXISTS a violating subquery row is true when there are no subquery rows at all. ANY would have the opposite empty-set truth value, false.
