**Independently derived answer:** i is even at each loop test

**Essential problem context (paraphrased):** Pascal enters the loop only if i mod 2=0. While i≥0, it replaces i by i div 2, then subtracts 1 if the new i is odd, otherwise subtracts 2. Give an invariant.

## Solution

The outer test establishes evenness before the first loop test. Let j be the quotient after the division in an iteration. If j is odd, j−1 is even; if j is even, j−2 is even. Thus either branch reestablishes the invariant regardless of the parity produced by division. Nonnegativity is the loop guard, not an invariant after the body: for i=0 the body produces −2 and terminates. An even negative initial value skips the loop altogether. The invariant states a preserved property, not a complete description of all reachable values.

**Official answer:** Not available; no official key located.

**Independently derived answer:** 7 in the optimal worst case

**Essential problem context (paraphrased):** What minimum number of comparisons suffices to sort five arbitrary distinct keys?

## Solution

There are 5!=120 possible strict orders, and a binary comparison tree of height six distinguishes at most 64 outcomes. Thus at least seven comparisons are necessary in the worst case. For sufficiency, sort two pairs (two comparisons), compare their larger elements (one), and rename them so a≤b≤d with c≤d. Insert the fifth key into a, b, d in at most two comparisons. Insert c into the prefix preceding d: at most three elements precede d, giving at most four possible positions and two further comparisons. Total: seven. This is a worst-case guarantee; a best-case successful path can be shorter.

**Independently derived answer:** D is the usual informative bound; B, D, E are valid upper bounds for connected simple graphs

**Essential problem context (paraphrased):** For n vertices and m edges, choices are A O(n²), B O(mn), C O(m+n), D O(m log n), E O(m²). Identify Kruskal’s complexity.

## Solution

Comparison-sort Kruskal first sorts m edges in O(m log m), then processes them with disjoint-set operations. For a connected simple graph, n−1≤m≤n(n−1)/2, so log m=O(log n), yielding O(m log n). This supports D. Because big-O is an upper bound, the same algorithm is also O(mn) and O(m²), so B and E cannot be called false merely for being looser in a multiple-answer task. O(m+n) is not the generic comparison-sorting bound; O(n²) does not cover the usual sorting cost for dense arbitrary-weight inputs. Different integer-sorting or presorted-edge models can change the analysis.

# GATE 1991: Q27 (printed A Q3(viii))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204230/GATE1991.pdf#page=3), physical page 3. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** MSQ, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** GFG: floor(√N)+1 (its B); Forum: ceil(√N)

**Essential problem context (paraphrased):** GFG initializes i=0 and repeats i:=i+1 while i*i≤N, then returns i. Forum instead prints i*i<N. Determine the return for positive N.

## Solution

For the non-strict GFG guard, the loop exits at the smallest integer i whose square exceeds N. That is floor(√N)+1, including a perfect square N=k², which returns k+1. For the strict Forum guard, the exit condition is i²≥N, so the smallest such integer is ceil(√N), returning k at a perfect square. For nonsquares both expressions coincide. For example, N=4 distinguishes 3 from 2. The source change therefore matters and is not a harmless formatting variation. This arithmetic analysis assumes i*i and the increment do not overflow the Pascal integer range.

# GATE 1991: Q62 (printed B Q13)

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204230/GATE1991.pdf#page=7), physical page 7. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 10 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Use a balanced search tree of distinct values and counts, then inorder expansion: O(n log(k+1)) time and O(k) auxiliary space; worst-case optimal in the comparison model.

**Essential problem context (paraphrased):** Give an optimal comparison-based algorithm, with pseudocode and analysis, to sort n numbers containing k distinct values; k is not known in advance.

## Solution

Maintain one node per distinct key in a balanced binary search tree, storing a frequency counter. Unlike a simple unbalanced BST, an AVL or red-black tree guarantees height O(log(d+1)) when d distinct values have been encountered. The algorithm discovers k automatically.

SORT_FEW_DISTINCT(A):
  T := empty balanced search tree
  for x in A:
    node := FIND(T,x)
    if node exists: node.count := node.count + 1
    else: INSERT_BALANCED(T, key=x, count=1)
  output := empty sequence
  for node in INORDER(T):
    repeat node.count times: append node.key to output
  return output

After each insertion, the tree contains exactly the distinct input values seen so far, with their correct multiplicities. Inorder traversal visits keys in increasing order, and expanding each count preserves all occurrences. Thus the output is a sorted permutation of the input.

Each of n updates costs O(log(k+1)); inorder traversal costs O(k), and emitting n values costs O(n). Total time is O(n log(k+1)), commonly written O(n log k) for k≥2. The +1 handles k=1, where the algorithm is linear. Auxiliary tree storage is O(k), excluding the n-element output; an array can be overwritten during the final traversal if the input need not be retained.

For worst-case comparison optimality at fixed n and k, consider balanced multiplicities among k ordered values. There are n!/(n1!…nk!) distinguishable orderings, where each ni is approximately n/k. A constant-branching comparison decision tree requires Ω(log(n!/(n1!…nk!)))=Ω(n log k) comparisons in the worst case for k≥2. Reading or writing the input/output also costs Ω(n), giving Ω(n log(k+1)) overall. This is a worst-case statement over multiplicities, not a claim of distribution-sensitive optimality for every frequency pattern. With bounded integer keys, counting/radix methods may bypass the comparison lower bound; without a key-universe assumption they are not a general replacement.
