**Essential problem context (paraphrased):** For n vertices and m presorted edges, state Kruskal’s running time and the union-find model.

**Independently derived answer:** D: radix sort

**Essential problem context (paraphrased):** Which listed method sorts n integers in [1, n³] in O(n): heapsort, quicksort, mergesort, radix sort?

## Solution

Subtract one to put keys in [0, n³−1], then represent each in base n using three digits. Stable counting sort of one digit takes O(n+n)=O(n) time and O(n) auxiliary storage, so three least-significant-digit passes remain linear. Comparison sorts retain their general Ω(n log n) worst-case comparison barrier on arbitrary distinct keys; the integer representation lets radix sorting escape that model. The bound assumes word operations and digit extraction on these O(log n)-bit keys take constant time.

**Independently derived answer:** Intended base-case-preserving reading: F(1)=3, F(n)=F(n−1)^n for n>1. Literal unconditional final assignment instead gives F(n)=1 for all n.

**Essential problem context (paraphrased):** The printed function initializes F1←1, tests n=1 and assigns F←3 in that case; otherwise it repeats i=1..n, setting C←0, incrementing C once for each j=1..F(n−1), then setting F1←F1*C. A final F←F1 appears after the loop, with ambiguous if/else grouping. n is positive. Derive a recurrence for the returned value F(n).

## Solution

First distinguish the function’s returned numerical value from its running time. In one outer iteration the inner loop increments C exactly F(n−1) times, so C=F(n−1). Starting from F1=1, the outer loop multiplies by that same value n times. Hence for n>1 the returned value is F(n)=∏[i=1..n] F(n−1)=[F(n−1)]^n. The base is F(1)=3 if the base-case assignment is returned without being overwritten.

A block-explicit rendition of this intended reading is:
function F(n):
  if n=1 then return 3;
  F1:=1;
  for i:=1 to n do begin
    C:=0;
    for j:=1 to F(n−1) do C:=C+1;
    F1:=F1*C
  end;
  return F1.
This explains why neither n·F(n−1) (a sum) nor a runtime recurrence answers the value question. For instance F(2)=3²=9 and F(3)=9³=729.

Source qualification: both reproductions place a final F=F1 after the if/else loop without clearly enclosing it in the else branch. Under a literal Pascal-like reading with that assignment executed unconditionally, n=1 first sets F=3 but then overwrites it with the initial F1=1. The recurrence becomes F(1)=1, F(n)=F(n−1)^n and all values are 1. The intended nontrivial recurrence therefore requires treating the final assignment as part of the else computation or returning immediately from the n=1 case. This control-flow assumption is explicit rather than silently repaired.

**Official answer:** Not available; no official key located.

**Independently derived answer:** Under intended base F(1)=3, F(n)=3^(n!). Under unconditional final-assignment reading, F(n)=1.

**Essential problem context (paraphrased):** The printed function initializes F1←1, tests n=1 and assigns F←3 in that case; otherwise it repeats i=1..n, setting C←0, incrementing C once for each j=1..F(n−1), then setting F1←F1*C. A final F←F1 appears after the loop, with ambiguous if/else grouping. n is positive. Solve the recurrence for a closed form.

## Solution

Using the base-case-preserving reading, F(1)=3 and F(n)=[F(n−1)]^n for n≥2. All values are positive, so define a_n=log₃F(n). Exponentiation becomes multiplication: a_1=1 and a_n=n a_(n−1). Repeated substitution gives a_n=n(n−1)…2·1=n!, hence F(n)=3^(n!).

An induction verifies the expression without logarithms. At n=1, 3^(1!)=3 equals the base value. If F(n−1)=3^((n−1)!), then F(n)=(3^((n−1)!))^n=3^(n·(n−1)!)=3^(n!). This completes the proof for every positive integer n. Checks at n=2 and n=3 give 9 and 729; n=4 yields 3^24=282429536481. Confusing 3^(n!) with (3^n)! or with 3^n would lose the repeated multiplication of exponents.

This formula describes the function’s value under unbounded-integer arithmetic, not the execution time or the size of a machine integer. The return value grows much faster than an ordinary exponential, and practical fixed-width implementations overflow quickly.

The source ambiguity remains material here. If the final F=F1 executes even after n=1 assigns F=3, the true base is 1. Induction on the same recurrence then gives F(n)=1 for all positive n. Thus 3^(n!) is an explicitly conditional intended solution; 1 is the literal unconditional-assignment solution. No verified official key resolves that control-flow formatting.

# GATE 1992: Q48 (printed B Q8)

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204205/GATE1992.pdf#page=6), physical page 6. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, Unallocated leaf; group total None mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Climb from both endpoints in parallel until one reaches the other original endpoint; print the successful parent path and the added closing edge.

**Essential problem context (paraphrased):** T is a depth-first tree of an undirected graph G. Only a parent array P is given, with the root its own parent. For non-tree edge (u,v), give Pascal-like code printing its unique cycle after addition to T, in time proportional to cycle length.

## Solution

In an undirected DFS tree, every non-tree edge joins an ancestor and a descendant. To see why, suppose an edge joined distinct DFS subtrees: while its first endpoint’s subtree was explored, the still-undiscovered other endpoint would be reached by that edge and placed in the same subtree, a contradiction. Thus the tree path between u and v is a single upward parent chain from the descendant. Which endpoint is deeper is not given, so climbing just one chosen endpoint can waste time or stick at the root.

Climb both parent chains in lockstep, saving both traversals, and stop as soon as one reaches the other original endpoint:
procedure PrintCycle(u,v);
begin
  a:=u; b:=v; lenA:=1; lenB:=1;
  pathA[1]:=u; pathB[1]:=v;
  while (a<>v) and (b<>u) do begin
    a:=P[a]; lenA:=lenA+1; pathA[lenA]:=a;
    b:=P[b]; lenB:=lenB+1; pathB[lenB]:=b
  end;
  if a=v then begin
    for k:=1 to lenA do write(pathA[k]);
    write(u)
  end else begin
    for k:=1 to lenB do write(pathB[k]);
    write(v)
  end
end.
Assume arrays can hold the tree height plus one and append/write are constant-time operations. Storage can instead be growable linked lists with constant-time append. Arrays need no initial clearing; only positions written above are read.

Let the ancestor–descendant distance be d. The descendant walk reaches the ancestor after exactly d rounds, even if the other walk has already reached the root and is repeating its self-parent. The algorithm performs at most 2d parent moves and prints d+1 distinct cycle vertices plus the repeated start: Θ(d+1), proportional to the cycle’s d+1 edges, with O(d+1) temporary storage. For example a parent chain 7→5→2 and new edge (2,7) prints 7,5,2,7.

No full-tree traversal, depth computation or global visited-array clearing is required. The argument assumes the usual simple undirected graph; a self-loop can be handled immediately by printing u,u. For an arbitrary spanning tree the ancestor property is false, so this algorithm is specifically justified by the DFS premise.
