

# GATE 1994: Q13 (printed A Q1.13)

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204113/GATE1994.pdf#page=2), physical page 2. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** MCQ, Unallocated leaf; group total None mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** B: FIFO

**Essential problem context (paraphrased):** A heavily used page was loaded early and remains in constant use. Which listed policy can evict it because of its age: LRU, FIFO, generic replacement, or none?

## Solution

FIFO orders resident pages by when they entered memory, ignoring later references. A page loaded early can therefore reach the front of the eviction queue even while frequently accessed. LRU updates recency information when the page is used, so constant recent use protects it relative to less recently referenced pages. The question contrasts these policy criteria, not an absolute guarantee that a page can never be evicted under any workload. FIFO’s load-age rule is the specific explanation.

# GATE 1994: Q21 (printed A Q1.21)

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204113/GATE1994.pdf#page=3), physical page 3. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** MCQ, Unallocated leaf; group total None mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** B under the total-program-overlay interpretation

**Essential problem context (paraphrased):** Which is true: nested macro definitions are impossible; overlays allow a program larger than address space; virtual memory exceeds address space; or high-level interrupt routines are impossible?

## Solution

An overlay design keeps only selected mutually exclusive program portions resident at once and loads others into reused addresses. Its total stored program can therefore exceed the simultaneously addressable space, provided each active configuration fits. Virtual memory can exceed installed physical RAM, but it does not by itself enlarge the architecture’s virtual address space. Nested macros and high-level interrupt routines are possible in suitable tools, so the blanket impossibility claims fail. GFG truncates words in C; the alternate explicitly says address space, not physical memory, which is essential to the distinction.

**Essential problem context (paraphrased):** The pictured heap has allocated lengths 50,300,600 separating free holes of lengths 150 and 350. Can requests 300,25,125,50 be satisfied by first fit, best fit, both or neither?

## Solution

Both policies allocate the first request in the 350 hole, leaving free lengths [150,50]. First fit places 25 in the first hole, leaving [125,50], then 125 there, leaving [0,50], and finally fits 50. Best fit places 25 in the 50 hole, leaving [150,25], then 125 in the 150 hole, leaving [25,25]. The final 50 fits neither hole, though total free space is 50. Hence only first fit succeeds. The labels are lengths, not boundary addresses; the alternate also omits NOT in option C, a separate transcription defect.

# GATE 1994: Q82 (printed B Q27(a))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204113/GATE1994.pdf#page=7), physical page 7. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, Unallocated leaf; group total 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Conservative guarded precedence: 1→3,2→3,3→4,4→5,5→6,3→6; execute 4,5 only on the false branch. The source needs a convention for “precedence graph”.

**Essential problem context (paraphrased):** The printed straight-line code is S1: read n; S2: i:=1; S3: if i>n goto next; S4: a(i):=i+1; S5: i:=i+1; S6: next: write a(i). No backward jump is printed. Draw its precedence graph, stating the treatment of conditional execution.

## Solution

The source calls for a precedence graph but contains a conditional jump, so an ordinary unguarded task DAG cannot by itself specify whether S4 and S5 execute. A faithful control-flow graph is S1→S2→S3, with S3 true→S6 and S3 false→S4→S5→S6. This edge list completely specifies the literal execution graph; there is no loop-back edge.

For potential parallel execution, S1 and S2 are independent initial tasks: the former writes n and the latter writes i. S3 needs both values, giving S1→S3 and S2→S3. On the false branch, keep S3→S4→S5→S6. S4 must precede S5 because it reads the old i both as an index and as the right-side operand; S5 changes i. S6 must see the incremented i on this branch. On the true branch, S6 follows S3 directly without executing S4 or S5. Thus a conservative guarded precedence description has edges 1→3,2→3,3→4,4→5,5→6,3→6, with 4 and 5 guarded by i≤n. The edge 3→6 describes the alternate branch, not an extra unconditional join requirement.

Do not conflate this graph with a pure data-dependence graph, which would omit some control edges and include direct uses of i. Also do not insert a guessed loop. With n≥1 the literal code assigns a(1), increments i to 2, then writes a(2), which it has not initialized. With n<1 it immediately writes a(1), also not initialized here. These are semantic concerns in the printed fragment, not permission to change its instructions. The question lacks enough conventions for a unique unqualified concurrency graph.

# GATE 1994: Q83 (printed B Q27(b))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204113/GATE1994.pdf#page=7), physical page 7. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, Unallocated leaf; group total 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Not with parbegin–parend alone preserving the conditional skip. With an ordinary conditional as well, S1 and S2 can run in parallel, followed by S3-controlled work.

**Essential problem context (paraphrased):** The printed straight-line code is S1: read n; S2: i:=1; S3: if i>n goto next; S4: a(i):=i+1; S5: i:=i+1; S6: next: write a(i). No backward jump is printed. Can its graph be converted into a concurrent program using parbegin–parend only?

## Solution

A parbegin–parend block starts all of its component branches and waits for them all to finish. It expresses fork/join synchronization, not a data-dependent choice to omit a branch. In the printed program S4 and S5 must be skipped if i>n, and must execute in order otherwise. Therefore an unconditional composition using only sequential composition and parbegin–parend cannot represent the exact conditional semantics. This is the sense in which the answer is no.

If ordinary conditionals are allowed alongside parbegin–parend, a simple equivalent ordering is: parbegin read n; i:=1 parend; if i≤n then begin a(i):=i+1; i:=i+1 end; write a(i). The first two statements have disjoint write sets, so running them concurrently is safe; the join ensures both values are ready before the test. The remaining statements retain their branch and anti-dependence order. This transformation preserves even the original fragment's possible uninitialized-array access; it does not repair it.

One must distinguish this semantic issue from the graph-theoretic claim that every precedence DAG can be expressed by nested fork/join. That latter claim is false in general, but no particular non-series-parallel graph should be asserted here without specifying which dependence convention produced it. The conservative dependency ordering of part (a), once branch guards are disregarded, is structurally fork/join compatible. The actual obstacle under the literal word “only” is conditional execution. If the examiner intended a different dependence-only graph or omitted loop, that intent is not established by either inspected reproduction.

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204113/GATE1994.pdf#page=7), physical page 7. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Official answer:** Not available; no official key located.

**Independently derived answer:** No, under the standard assumption that a process finishes and releases its holdings after its depicted requests are granted.

**Essential problem context (paraphrased):** Resource types r1,r2,r3 have respectively 2,3,2 instances. Assignments are r1→P1 and r1→P0; r2→P1, r2→P2 and r2→P3; r3→P0, leaving one r3 instance free. Outstanding requests are P1→r1; P0→r2 and P0→r3; P2→r3; P3→r1 and two P3→r2 arrows. Does the depicted resource-allocation graph represent deadlock?

## Solution

Read each dot-to-process arrow as an allocated instance and each process-to-resource arrow as an outstanding request. In resource order (r1,r2,r3), total resources are (2,3,2). The allocation rows are P0=(1,0,1), P1=(1,1,0), P2=(0,1,0), P3=(0,1,0); their sum is (2,3,1), leaving Work=(0,0,1). The request rows are P0=(0,1,1), P1=(1,0,0), P2=(0,0,1), P3=(1,2,0). The two parallel P3→r2 arrows mean two requested instances, not a duplicated decorative edge.

Initially P2 is the process whose request vector is componentwise at most Work. Give it the free r3 instance. Under the standard graph-reduction model it completes, releasing that temporary grant and its held r2 instance. Consequently Work increases by its original allocation, from (0,0,1) to (0,1,1). P0 can now receive its requested r2 and r3 instances and complete, increasing Work to (1,1,2). P1 can then finish and increase Work to (2,2,2). Finally P3's request (1,2,0) is satisfiable, so it also completes.

All process nodes can be removed, so the current graph does not describe a deadlock. Cycles alone are insufficient to infer deadlock when resource types have multiple instances. This is a reduction of the displayed current requests, not a claim of Banker safety against unknown additional future maximum demands; no such maxima are supplied.

**Type / marks:** descriptive, Unallocated leaf; group total 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** P2 → P0 → P1 → P3.

**Essential problem context (paraphrased):** Resource types r1,r2,r3 have respectively 2,3,2 instances. Assignments are r1→P1 and r1→P0; r2→P1, r2→P2 and r2→P3; r3→P0, leaving one r3 instance free. Outstanding requests are P1→r1; P0→r2 and P0→r3; P2→r3; P3→r1 and two P3→r2 arrows. If the system is not deadlocked, give a safe completion sequence.

## Solution

Use the available-vector test in resource order (r1,r2,r3). Initially Work=(0,0,1). P2 requests (0,0,1), so its request fits. On completion its original holding (0,1,0) returns to the available pool, giving Work=(0,1,1). It is important not to count the temporarily granted r3 twice: allocation-based reduction adds only the allocation it held before this simulated completion.

Next P0 requests (0,1,1), exactly within Work. It finishes and releases original allocation (1,0,1), making Work=(1,1,2). P1's outstanding request (1,0,0) now fits; releasing its original allocation (1,1,0) gives Work=(2,2,2). P3 can finally receive (1,2,0); releasing its original holding (0,1,0) gives Work=(2,3,2), the complete resource inventory. Thus P2,P0,P1,P3 is a valid completion sequence.

Indeed the initial choices are forced by the displayed requests: P0 initially lacks r2, while P1 and P3 lack r1. After P2, P0 is the only remaining satisfiable process. After P0, P3 still needs two free r2 instances but only one is available, forcing P1 before P3. Under simultaneous satisfaction of the displayed request vectors this order is therefore unique. As in part (a), “safe” means all these displayed requests can be satisfied and the processes finish; the graph does not state maximum possible future claims, so a stronger Banker's-algorithm safety assertion is outside the supplied data.
