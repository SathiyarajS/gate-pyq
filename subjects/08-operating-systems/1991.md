**Independently derived answer:** It must admit a series-parallel decomposition

**Essential problem context (paraphrased):** What property must a process precedence graph have to be expressed using only properly nested parbegin/parend and sequential composition?

## Solution

A sequential composition places every process in one component before every process in the next. A parbegin/parend composition runs its child components independently and joins after all finish. Starting from individual processes and repeatedly applying these two constructions yields the series-parallel class of precedence structures. Conversely, its recursive decomposition directly supplies a nested program. An arbitrary acyclic graph can contain cross-dependencies that cannot be represented by these nested constructs alone without extra synchronization or unnecessary ordering. The statement concerns the precedence relation, allowing omission of redundant transitive edges.

**Essential problem context (paraphrased):** Match buddy system, interpretation, virtual memory, pointer with P runtime type checking; Q segmentation; R memory allocation; S garbage collection.

## Solution

Buddy allocation splits power-of-two blocks and merges free buddies, so R is direct. Segmentation is one way to implement a virtual address space, making Q the intended virtual-memory association. Dynamically typed interpreters commonly check types during execution, suggesting P. Pointer reachability underlies tracing garbage collection, suggesting S. The last three are associations, not necessities: interpreters can execute statically typed languages, virtual memory can use paging rather than segmentation, and pointer-supporting languages need not provide garbage collection. The matching should not be promoted into universal implementation laws.

## Solution

Monitors enforce mutual exclusion but can still deadlock through circular waits, so C is false. Best fit may leave many tiny holes, so E is false. Yet they still rely on indivisible basic accesses in the usual model, so the broader literal claim about any indivisible instruction is not refuted that way. A conventionally concerns committed backing capacity, not virtual-address-space width. The common intended false set B, C, E is conditional on those readings. Forum’s omitted monitor claim and “hashing” typo prevent blindly transferring letters.

# GATE 1991: Q56 (printed B Q11(a))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204230/GATE1991.pdf#page=7), physical page 7. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Yes, under atomic reads/writes and sequential consistency; this does not guarantee progress.

**Essential problem context (paraphrased):** Shared atomic variables: flag[0..2] initially false; turn in {0,1,2}. For process i let j=(i+1) mod 3 and k=(i+2) mod 3. Repeat:
  flag[i] := true
  while flag[j] or flag[k]:
    case turn:
      j: if flag[j]:
           flag[i] := false
           while turn != i: skip
           flag[i] := true
      k: if flag[k]:
           flag[i] := false
           while turn != i: skip
           flag[i] := true
  critical section
  if turn == i: turn := j
  flag[i] := false
  noncritical section
Does this scheme ensure mutual exclusion? Explain.

## Solution

First separate safety from liveness. A process sets its flag true before testing the outer while condition, and a process admitted to its critical section keeps that flag true until after leaving the critical section. Withdrawing its flag happens only inside the entry loop, never while it is in the critical section.

Suppose two distinct processes p and q were simultaneously in their critical sections. Consider the final assignments flag[p]=true and flag[q]=true preceding these particular admissions. Assume p's assignment occurred first. Its flag remains true from that assignment through its critical section: if it had withdrawn and raised the flag again, the assignment chosen was not final. Process q performs its successful outer test after its own final assignment, hence after p's final assignment. If q enters while p is still inside, q must encounter flag[p]=true and cannot pass the test. If p has already left when q reads false, the two critical sections do not overlap. This contradiction proves mutual exclusion. The argument works with separate atomic flag reads as well: a continuously true competing flag cannot be read as false.

The turn variable controls who backs off, but the persistent true flag is the safety invariant. No fairness assumption is needed for this safety proof. Atomic coherent shared-memory operations are needed; the bare pseudocode is not automatically a correct implementation on a weak-memory machine without suitable synchronization.

# GATE 1991: Q57 (printed B Q11(b))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005204230/GATE1991.pdf#page=7), physical page 7. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Yes. Two contenders can spin forever when turn names an inactive third process. A three-process bakery lock is a correct replacement.

**Essential problem context (paraphrased):** Shared atomic variables: flag[0..2] initially false; turn in {0,1,2}. For process i let j=(i+1) mod 3 and k=(i+2) mod 3. Repeat:
  flag[i] := true
  while flag[j] or flag[k]:
    case turn:
      j: if flag[j]:
           flag[i] := false
           while turn != i: skip
           flag[i] := true
      k: if flag[k]:
           flag[i] := false
           while turn != i: skip
           flag[i] := true
  critical section
  if turn == i: turn := j
  flag[i] := false
  noncritical section
Can a waiting process fail forever to enter? Give an execution and a corrected algorithm.

## Solution

Take turn=2, with process 2 remaining in its noncritical section and flag[2]=false. Let processes 0 and 1 both set their flags true before either completes its outer test. Each sees the other's true flag. Its case selects process 2, but the guarded branch sees flag[2]=false, so neither process withdraws or changes turn. They repeat forever, even under fair scheduling of all active processes. Only a critical-section exit changes turn, and neither contender can reach such an exit. Thus progress fails, not merely a timing bound. An inner waiter can also be stranded when turn is handed to an inactive process.

A safe repair is to replace the entire entry/exit protocol with Lamport's bakery algorithm, rather than merely skipping a false flag: false can mean a temporarily withdrawn waiter, not an uninterested process. Use separate choosing and ticket arrays, initially false and zero. Atomic reads/writes and sequential consistency are assumed, and mathematical tickets are unbounded integers.

For process i:
  choosing[i] := true
  ticket[i] := 1 + max(ticket[0], ticket[1], ticket[2])
  choosing[i] := false
  for r := 0 to 2, r != i:
    while choosing[r]: skip
    while ticket[r] != 0 and (ticket[r],r) < (ticket[i],i): skip
  critical section
  ticket[i] := 0
  noncritical section
  repeat

Pairs are compared lexicographically, first by ticket and then process number. The choosing flag prevents observing a half-completed ticket selection as if the process were absent. If two processes competed to enter, the one with larger pair must wait for the smaller pair's nonzero ticket; both cannot be inside together. A process which starts choosing after i has published its ticket obtains a larger ticket and cannot overtake i. Only finitely many already competing choices can precede i. Under fair scheduling, finite ticket-selection and critical-section execution, and no process failures, those predecessors finish, so i eventually enters. An inactive process has choosing=false and ticket=0 and is ignored. These assumptions are necessary: no software lock can promise entry if its current owner stops forever.
