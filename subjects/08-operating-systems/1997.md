**Official answer:** Not available; no official key located.

**Independently derived answer:** B

**Essential problem context (paraphrased):** A page reference always repeats the previous page, is likely among recently used pages, always hits resident memory, or always faults.

## Solution

Temporal locality is the tendency to reuse recently accessed data or instructions, for example within a loop. Hence the next page reference is likely to be among a recent working set, B. This is a statistical tendency, not an absolute guarantee. A program can move to a new phase and access a different page, and whether that page is resident depends on available memory and replacement history. Thus the three statements containing always are too strong.

**Essential problem context (paraphrased):** Nine processes repeat P(mutex);critical section;V(mutex). A tenth replaces its initial P by V. What maximum number can be inside simultaneously?

## Solution

The faulty process never consumes a permit when entering and adds permits both before entering and after leaving. With a counting semaphore, it can complete enough loops to accumulate at least nine permits while the others wait to run. Then schedule all nine correct processes through P and pause each inside its critical section. Finally let the faulty process enter too: all ten are inside. Ten is the absolute upper bound because only ten processes exist, so it is attained. Even a saturating binary semaphore can be repeatedly reopened by the faulty process to admit more peers before they leave. Thus D.

# GATE 1997: Q93 (printed B QGFG73)

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203902/GATE1997.pdf#page=11), physical page 11. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 5 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** Under mutex, select the highest set request flag, clear it and signal that process while retaining busy=true; set busy=false only if no process waits.

**Essential problem context (paraphrased):** Three processes use a shared resource R mutually exclusively and nonpreemptively. Each has a unique fixed priority in {1,2,3}, with 3 highest. Shared state: semaphore mutex=1; semaphores proceed[1..3]=0; Boolean R_requested[1..3]=false; Boolean busy=false. Each process repeats request_R(my_priority); P(proceed[my_priority]); use R; release_R(my_priority). The supplied request_R(p) performs P(mutex); if busy then R_requested[p]:=true else begin V(proceed[p]); busy:=true end; V(mutex). Give release_R so each allocation goes to the highest-priority current requester. The shared-data declaration is printed as process[3] in the reproduction, while uses consistently say proceed; normalize that apparent naming typo explicitly.

## Solution

The release operation must inspect request flags and either transfer ownership or mark the resource free as one atomic critical section. Otherwise a new requester could take R between checking the flags and waking a waiting process. This code uses the same proceed array as the process and request routines; the source's isolated process spelling is treated as a declaration typo.

procedure release_R(my_priority):
    P(mutex)
    chosen := 0
    for p := 3 downto 1 do
        if R_requested[p] then
            chosen := p
            break
    if chosen = 0 then
        busy := false
    else
        R_requested[chosen] := false
        busy := true
        V(proceed[chosen])
    V(mutex)

The parameter my_priority identifies the releasing owner but is not needed to select the next one. Preconditions are that only the current owner calls release_R, each process has at most one outstanding request, and P/V have standard semaphore semantics. The no-waiter branch does not signal a semaphore: the next arriving requester will signal its own proceed entry in request_R before doing P on it.

Why keep busy true during handoff? A signaled process may not run immediately. The resource is nevertheless reserved for it; setting busy false would let a newcomer receive a second grant. Clearing the chosen flag prevents a later release from treating the same already-granted request as still waiting. Lower-priority flags remain set, preserving their requests.

Since priorities are unique and the loop scans 3,2,1, it chooses the highest pending priority at the moment of allocation. A higher-priority process arriving after that atomic choice must wait: the resource is nonpreemptive, so priority does not revoke an existing grant. At most one grant exists at a time, maintaining mutual exclusion. This scheme can starve a low-priority requester if higher-priority requests keep arriving; starvation freedom was not requested and does not follow from strict priority allocation.

# GATE 1997: Q94 (printed B QGFG74(a))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203902/GATE1997.pdf#page=11), physical page 11. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 1 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** 17,000 ms = 17 s.

**Essential problem context (paraphrased):** A program processes 1000 consecutive records of a sequential file on a device, without file-system facilities. Each record is 3200 bytes. Device access time is 10 ms per read; transfer rate is 800×10^3 bytes/s; CPU processing time is 3 ms per record. Copying a record from a buffer to a local variable takes negligible CPU time. Ignore additional overhead, and include startup and final processing time. Records are unblocked and the program uses no buffering. Find elapsed time.

## Solution

One record's transfer time is its byte count divided by the byte rate:
3200/(800×10^3) seconds = 0.004 seconds = 4 ms.
The 10 ms access time is a separate per-read cost, so reading one unblocked record takes 10+4=14 ms. With no buffering, the program reads a record, waits for that read to finish, processes it for 3 ms, and only then starts the next record's read.

The per-record serial schedule is therefore [10 ms access][4 ms transfer][3 ms processing], lasting 17 ms. Repeating it for 1000 records gives 1000×17=17,000 ms=17 seconds. The first record's access and the last record's processing are already included, so no extra startup or drain term should be appended.

The word consecutive does not by itself remove the explicitly supplied access cost. The usual model of this question charges one access for each unblocked read; a continuous streaming device model that pays access only once would be a different assumption. Likewise, the rate is in bytes per second, so no factor of eight belongs in the calculation. The result uses the decimal rate 800×10^3 exactly as printed.

Without read-ahead storage there is no valid overlap between reading the next record and processing the current one in this model. Using max(14,3) per record would silently introduce buffering, which is the separate next part of the question.

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203902/GATE1997.pdf#page=11), physical page 11. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Official answer:** Not available; no official key located.

**Independently derived answer:** 14,003 ms = 14.003 s, under the stated ideal one-buffer read-ahead model.

**Essential problem context (paraphrased):** A program processes 1000 consecutive records of a sequential file on a device, without file-system facilities. Each record is 3200 bytes. Device access time is 10 ms per read; transfer rate is 800×10^3 bytes/s; CPU processing time is 3 ms per record. Copying a record from a buffer to a local variable takes negligible CPU time. Ignore additional overhead, and include startup and final processing time. Records are unblocked and the program uses one buffer, always reading ahead into it. Find elapsed time.

## Solution

A record read takes 10 ms access plus 3200/(800×10^3) seconds transfer, or 14 ms total. The first read fills the buffer at t=14 ms. Copy record 1 into the program's local record variable at negligible cost, freeing the buffer immediately. The device can now read record 2 while the CPU processes record 1.

The timeline begins:
0–14 ms: read record 1; CPU has no record yet.
14–17 ms: process local record 1; read record 2 during 14–28 ms.
28–31 ms: process local record 2; read record 3 during 28–42 ms.

Because each read lasts 14 ms and each computation only 3 ms, the CPU finishes before the next record arrives. Record k is available at 14k ms. The final record, number 1000, arrives at 14,000 ms and must still be processed for 3 ms. Total elapsed time is 14,000+3=14,003 ms.

Equivalently, for N records, read time I and compute time C, this ideal single-record-buffer/local-variable pipeline takes I+(N−1)max(I,C)+C. Here it becomes 14+999×14+3. This formula includes the initial fill and final drain. The common shortcut N×max(I,C) would miss the last 3 ms.

One buffer is enough because the current record is moved out of that buffer before processing; CPU work uses the local copy while the device writes the next record to the buffer. This is not the same as processing in place in the sole buffer, which would prevent safe read-ahead. The source's negligible-copy assumption is what permits the overlap.

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203902/GATE1997.pdf#page=11), physical page 11. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Official answer:** Not available; no official key located.

**Independently derived answer:** 10.503 s with one-record local storage and reads starting only after the entire buffer is free; 9.006 s with whole-block local staging or sufficiently early access-phase overlap. The source does not fix these scheduling details.

**Essential problem context (paraphrased):** A program processes 1000 consecutive records of a sequential file on a device, without file-system facilities. Each record is 3200 bytes. Device access time is 10 ms per read; transfer rate is 800×10^3 bytes/s; CPU processing time is 3 ms per record. Copying a record from a buffer to a local variable takes negligible CPU time. Ignore additional overhead, and include startup and final processing time. The file uses blocking factor 2: each device block contains two records. The program uses one buffer. Find elapsed time, explicitly stating when the next read may begin and whether the program can retain a whole block outside the buffer.

## Solution

There are 1000/2=500 blocks. Each block holds 6400 bytes, so its transfer takes 6400/(800×10^3)=0.008 s=8 ms. Including the 10 ms access, one block read takes I=18 ms. Processing its two records takes 6 ms total. The words one buffer do not alone determine how the unread second record is protected while another read is started.

Model 1: one block buffer, one-record local variable, and a new block-read operation starts only after the buffer is entirely free. The first block arrives at t=18 ms. Copy record 1 locally and process it during 18–21. Record 2 must remain in the buffer during that computation. At 21, copy record 2 locally; the buffer is now free, so start the second block read during 21–39 while processing record 2 during 21–24. Thus each block arrival is 21 ms after the preceding one, not 18 ms: three CPU milliseconds are needed before the unread second record can leave the buffer.

The kth block arrives at 18+(k−1)×21 ms. For block 500 this is 10,497 ms. After it arrives, both final records still require 6 ms, giving 18+499×21+6=10,503 ms=10.503 s. Only the last record of each nonfinal block overlaps the following read. This schedule never overwrites a record that has not been copied out.

Model 2: copy the whole two-record block into separate local staging at negligible cost, releasing the input buffer immediately. Then all 6 ms of computation can overlap the following 18 ms read. The pipeline time is 18+499×max(18,6)+6=9006 ms=9.006 s. This model needs enough staging for two records, not just the single local record explicitly used in Model 1.

A second way to attain 9.006 s is to allow the next device access phase to begin before the buffer is free, while delaying actual writes until it is safe. Start the next 10 ms access immediately when the prior block arrives. The buffer's remaining record is copied out after 3 ms, well before the subsequent 8 ms transfer begins. Block arrivals can then remain 18 ms apart even with one-record local storage. That requires an I/O interface/scheduler that supports this early access, which the question does not explicitly describe.

Accordingly 9.006 s is the conventional whole-block-pipeline result, and 10.503 s is the stricter one-record/cannot-start-until-free result. Neither should be presented as unconditionally forced by the supplied wording. The distinction is about storage and I/O scheduling, not the arithmetic of the 18 ms block read.

# GATE 1997: Q97 (printed B QGFG75(a))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203902/GATE1997.pdf#page=12), physical page 12. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 3 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** No resource deadlock: every wait-for edge points from a younger process to an older process, so a cycle is impossible.

**Essential problem context (paraphrased):** Each process receives a unique timestamp when it starts, increasing with time; smaller means older. On requesting a resource: if it is free, the OS grants it; if holder Q is older than requester P (TS(Q)<TS(P)), P waits; if Q is younger (TS(Q)>TS(P)), the OS restarts Q and grants the resource to P. Restarting takes back all Q's resources, kills Q, and starts it again with the same timestamp. When a resource is released, the waiting process with smallest timestamp receives it. A process asks for resources, uses them for some time, then exits. Can deadlock ever arise? Prove your answer.

## Solution

Form a wait-for graph whose vertices are active processes. Add an edge P→Q when P is blocked waiting for a resource currently held by Q. The rules allow that wait only when TS(Q)<TS(P). If the holder is younger, the requester does not wait; it wounds the holder, whose resources are released on restart. Therefore timestamps strictly decrease along every wait-for edge.

Suppose a resource deadlock existed. For ordinary exclusive resources, a finite set of processes each blocked on resources held within the set contains a directed cycle P1→P2→…→Pk→P1. The edge rule would imply
TS(P1)>TS(P2)>…>TS(Pk)>TS(P1),
which is impossible for distinct ordered timestamps. Thus the wait-for graph is acyclic and the stated resource protocol cannot create deadlock.

For intuition, an older process can force a younger holder to release its resources rather than becoming dependent on it. A younger process may depend on an older one, but dependencies can never turn back toward a younger timestamp to close a cycle. This is the wound-wait scheme, not wait-die: the older requester survives and restarts the younger holder.

The restart must release all resources of the victim, as the source explicitly states; retaining them while the victim cannot proceed would not implement this proof's protocol. Resource grants, victim removal and wait-queue updates are assumed to be performed consistently by the OS. The argument rules out resource deadlock, not every possible lack of progress. An unfair CPU scheduler or a process that never finishes could still delay other processes indefinitely; those are separate starvation/liveness issues addressed under additional assumptions in the next part.

# GATE 1997: Q98 (printed B QGFG75(b))

**Question:** [Third-party reproduction](https://media.geeksforgeeks.org/wp-content/cdn-uploads/20211005203902/GATE1997.pdf#page=12), physical page 12. Consult the reproduced wording and choices. Original official provenance and completeness have not been established.

**Type / marks:** descriptive, 2 mark(s).

**Official answer:** Not available; no official key located.

**Independently derived answer:** No protocol-induced starvation under finite older predecessors, finite terminating work, and fair execution; an unconditional guarantee without these progress assumptions is not justified.

**Essential problem context (paraphrased):** Each process receives a unique timestamp when it starts, increasing with time; smaller means older. On requesting a resource: if it is free, the OS grants it; if holder Q is older than requester P (TS(Q)<TS(P)), P waits; if Q is younger (TS(Q)>TS(P)), the OS restarts Q and grants the resource to P. Restarting takes back all Q's resources, kills Q, and starts it again with the same timestamp. When a resource is released, the waiting process with smallest timestamp receives it. A process asks for resources, uses them for some time, then exits. Can a process be starved? Prove or qualify your answer.

## Solution

Fix a process P. When it begins there are only finitely many older processes in the usual finite-system model, and every later arrival has a larger timestamp. Because a restarted process keeps its original timestamp, repeated restarts do not move P behind newcomers. Only processes older than P can wound it or outrank it on a waiting queue.

First consider the oldest active process. It cannot be wounded, and it cannot be forced to wait for a younger holder: it wounds that holder and obtains the resource. Under fair CPU execution and the stated assumption that a process does finite work and exits, this oldest process eventually completes and releases its resources. Apply the same argument successively to the remaining older processes. Since P has finitely many older predecessors, eventually they have all completed.

P is then the oldest remaining process. New arrivals remain younger and cannot wound P. A resource held by a younger process is obtained by wounding that holder; if P is already waiting when a resource is released, smallest-timestamp selection gives it precedence over younger waiters. With finite resource requests/work and fair execution, P therefore finishes. This proves absence of starvation caused by the allocation protocol under the usual progress assumptions.

Retaining timestamps is crucial. Assigning a fresh, ever-larger timestamp after every restart would destroy the fixed finite-predecessor argument. Conversely, deadlock freedom by itself would not prove starvation freedom: an acyclic system could still repeatedly favor newcomers under a different queue rule.

The question's finite-use-and-exit wording motivates the normal no-starvation answer, but scheduler fairness is not explicitly specified. If the CPU never schedules P, or an older process never finishes, P may wait indefinitely despite the timestamp rules. Those countermodels violate the progress assumptions used in the proof; they do not exhibit a starvation defect in wound-wait itself. State the assumptions rather than claiming unconditional termination from timestamp ordering alone.
